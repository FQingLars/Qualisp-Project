# Глава 5. Модель памяти: scratch и world

Модель памяти Qualisp — **HibLin**: данные по умолчанию одноразовые и живут в
скоупе своего хранилища, а всё, что нужно сохранить, явно копируется в мир
`world`. Никакого GC, счётчика ссылок и ручного `free` для значений языка нет.
Основа — четыре механизма: `Store` с регионами `scratch`/`world`, методы
`Runtime.allocTensor`/`resetScratch`/`cloneToWorld`, неподвижная bump-арена
кадров вызова и `TensorBufferPool` для промежуточных тензоров HLO-графа.

## 5.1 Аналогия с черновиком

Решая пример в столбик на бумаге, вы пишете исходные числа на черновике,
промежуточный результат — тоже на черновике, а в чистовик переписываете только
ответ. Черновик выбрасывается.

HibLin работает так же: данные по умолчанию **одноразовые** (disposable).
Сохранить их можно только явным переписыванием — `defvar`, которое делает
глубокую копию в `world`. Промежуточные значения живут в текущем скоупе и
исчезают вместе с ним. Никакой «карточки со счётчиком читателей» здесь нет:
нужна копия — сделайте её.

> 🐍 **Python-аналогия.** В Python всё живёт в heap, и GC периодически
> освобождает недостижимые объекты. Здесь освобождение детерминированное:
> скоуп кончился — регион `scratch` откачен, кадр возвращён арене, тензор
> освобождён. Никаких GC-пауз и финализаторов.

## 5.2 Три правила

| Правило | Что означает | Аналогия |
|---|---|---|
| 1. Скоуп — граница вычисления | Скоуп создают вызов функции, top-level форма и итерация `while`; `let` и `progn` скоупа не создают | Каждый шаг решения в столбик — своя строка черновика |
| 2. Значение живёт в своём хранилище | Одноразовые значения умирают на конце скоупа; сохранённые через `defvar` живут в `world` | Черновик и тетрадь: переписал — черновик больше не нужен |
| 3. Побег в `world` — явная копия | `cloneToWorld` глубоко копирует значение; `world` никогда не ссылается на `scratch` | Копия в чистовике не зависит от черновика |

Главное следствие: внутри скоупа значения **перемещаются**, через границу —
**копируются**. Это и есть контракты времени жизни (LC, §5.5).

## 5.3 Хранилища и пулы

| Хранилище | Что держит | Механизм |
|---|---|---|
| `Store` / `scratch` | cons-ячейки, байты строк, мастер-формы текущей формы | bump-регион, `mark()`/`restore()`, полный сброс на границе формы |
| `Store` / `world` | `defvar`, глобалы, веса, код-как-данные | bump-регион, живёт до `clear`/teardown |
| `Runtime.frame_area` | кадры вызовов JIT-функций | одна неподвижная bump-арена, строго LIFO, `takeFrame`/`giveFrame` |
| `TensorBufferPool` | промежуточные буферы HLO-графа | free list точного размера по `(len, alignment)`; только HLO |

> 🐍 **Python-аналогия.** Как если бы PyTorch держал четыре цеха: один — под
> черновик формы, второй — под веса модели, третий — под кадры вызовов, четвёртый
> — под промежуточные активации графа. Ни один из них не «собирает мусор».

Кадровая арена — один неподвижный слот `frame_area` с указателем
`frame_top`. Ёмкость в коде — `1024 * 1024` слотов (порядка 24 МБ адресного
пространства, память трогается по мере глубины). Кадр живёт ровно до возврата
своего вызова, поэтому свободных списков не нужно: освобождение — вычитание
размера, а в Debug ещё и сверка указателя (нарушение LIFO падает в тестах).
Хвостовой вызов с более широким кадром меняет кадр через `replaceFrame`, а
`Runtime.tail_frame` помечает кадр, который освободит точка входа после возврата
всей цепочки.

Исчерпание арены — **не** OOM, а типизированная ошибка с позицией: хелпер зовёт
`bailAt(@returnAddress(), "call depth limit exceeded")`, позиция попадает в
`Runtime.error_location`, а CLI печатает `file:line:col: message` (или
`error: RuntimeError` в REPL). Чтобы машинный стек не умер раньше диагностики,
CLI поднимает лимит до 256 МБ (`raiseStackLimit`), а Windows-сборка резервирует
те же 256 МБ в PE-заголовке.

## 5.4 Два мира данных

```text
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  SCRATCH (disposable)        │     │  WORLD (persistent)         │
│                              │     │                              │
│  cons-ячейки текущей формы   │     │  defvar / глобалы            │
│  локальные биндинги          │     │  веса и параметры            │
│  промежуточные тензоры       │     │  мастер-формы defun/defgraph │
│  кадры вызовов               │     │  код-как-данные, макросы     │
│                              │     │                              │
│  Живут до конца скоупа.      │     │  Живут до clear / teardown.  │
│  Выход — reset/restore.      │     │  Смерть — снятие биндинга.   │
└─────────────────────────────┘     └─────────────────────────────┘
```

Мост между мирами — `Runtime.cloneToWorld`: обход `Value` и глубокая копия cons,
строк, структур, result, функций и тензоров в `world`. Повторная копия тензора с
`owner == .world` — no-op. Через мост проходят `defvar`, promotion из `while` и
результат top-level формы.

### `resetScratch`: граница формы

`Runtime.resetScratch` принимает mark текущего скоупа и освобождает всё, что
было аллоцировано после него: scratch-тензоры, cons-ячейки, кадры замыканий и
result-значения. `restoreLoop`/`rewindLoop` делают то же для итерации `while`,
не сбрасывая сам mark. Top-level форма тоже оставляет после себя чистый scratch.

### Времена жизни градиентов

Промежуточные активации графа живут в per-run `TensorBufferPool` и освобождаются
после `grad!` или в конце формы; результат `grad!` читается из последнего
запуска графа. Градиент `param`-тензора копируется в `world` и хранится прямо в
`Tensor.grad`; `grad-of` для ещё не считанного параметра возвращает нули той же
формы и dtype.

## 5.5 Контракты времени жизни (LC)

Контракты времени жизни — это правила, по которым значение переживает (или не
переживает) границу скоупа. Ниже — десять таких контрактов; все они следуют из
трёх правил §5.2.

### 5.5.1 Границы скоупа

Скоуп создают вызов функции, top-level форма и итерация `while`. `let` биндит в
текущем скоупе, `progn` — просто последовательность. Mark скоупа — это пара
`Store.Mark` + `ScratchMark`; откат — одна запись, его цена не зависит от числа
созданных значений. Возвращаемое значение копируется в родительский скоуп.

### 5.5.2 Скретч и world: копия, не алиас

`(defvar b a)` создаёт копию `a` в `world`, а не второе имя для того же объекта.
`setq` локального биндинга меняет значение в текущем скоупе; `setq` глобала
проходит через `cloneToWorld`. `nil`, `t` и символы бессмертны.

### 5.5.3 Передача значения

Внутри скоупа значение перемещается: лишних копий нет. При записи в более
долгоживущее хранилище вызывается `cloneToWorld`. Замыкание захватывает локальные
биндинги копией в своём доме; глобалы резолвятся live.

### 5.5.4 Время жизни world-значения

World-объект живёт до `clear` имени или до teardown. `clear` отвязывает имя —
после него `(defvar z …)` + `(clear z)` делает `z` снова unbound. Физическое
освобождение world-объектов и JIT-страниц происходит при teardown.

### 5.5.5 Правило корня

`world` никогда не ссылается на `scratch`. Запись молодого значения в старое
хранилище — глубокая копия; поэтому откат scratch не может оставить висячую
ссылку в глобале, весе или структуре. Это свойство построения, а не проверка на
каждой записи.

### 5.5.6 Владелец тензора

`Owner ∈ {scratch, world, pool}`: `scratch` — eager-тензор текущего скоупа,
`world` — копия в `defvar`/параметре, `pool` — буфер HLO-графа из
`TensorBufferPool`. `Runtime.allocTensor` создаёт zeroed тензор и регистрирует
его в scratch; `resetScratch` освобождает такие тензоры; `cloneToWorld` делает
глубокую копию. Устройства в перечислении нет — весь буфер лежит в памяти хоста.

### 5.5.7 cons-ячейки через Store

cons-ячейки и байты строк выделяются только через `Store` (scratch или world).
Обходящий `Store` аллокатор выпал бы из mark/restore и сделал бы откат
невозможным.

### 5.5.8 Writable views нет

`reshape`, `transpose`, `t-shape`, `t-column`, `t-rows` и `t-select-rows`
возвращают новые тензоры-копии. Writable view, через которое можно было бы
писать в чужой буфер, в языке нет. Мутировать можно только сам тензор —
`tset!`.

### 5.5.9 Наблюдаемость и диагностика

Счётчиков и команд диагностики памяти как языкового API нет. Ошибки памяти и
глубины — это диагностика со спаном;
исчерпание арены кадров даёт `call depth limit exceeded` с позицией (§5.3).
Проверяемость контракта обеспечивают тесты, типизированная ошибка рантайма и
отказ компиляции, а не alist со счётчиками.

### 5.5.10 Честные границы модели

- JIT-страницы и скомпилированные HLO-графы — выбрасываемый кэш, выведенный из
  мастер-формы; их смерть не является семантическим событием.
- `eval` — единственное место, где статический тип проверяется в рантайме.
- Мутабельные world-структуры могут образовывать цикл; он не собирается до
  teardown — осознанная цена отсутствия GC.
- `clear` снимает callable/значение, но граф и JIT-страница живут до teardown.

> 🐍 **Python-аналогия.** Это не `weakref` и не `del` «в нужных местах»: границы
> жизни заданы скоупами и копированием при записи, а нарушение ловится ошибкой со
> спаном, а не через просмотр счётчиков.

## 5.6 Операции и их владение

| Операция | Входы | Выход | Где живёт |
|---|---|---|---|
| `(+ x y)`, `(matmul x w)` | читаются, не потребляются | новый тензор | scratch |
| `(defvar w (:tensor …) val)` | `val` нетронут | глубокая копия | world |
| `(setq w val)` глобальной | — | копия через `cloneToWorld` | world |
| `(setq x val)` локальной | — | значение в текущем скоупе | scratch |
| `(defun f …)`, `(defmacro m …)` | — | функция с захваченным окружением | world |
| `(reshape t …)`, `(transpose t)` | `t` не меняется | копия | scratch |

Файловые хэндлы — отдельный канал: это `:fixnum`-токены поверх `std.Io.File`,
а не значения `scratch`/`world`. Их закрывает макрос `with-file` из модуля `io`:

```lisp
(import io)

(with-file (f "/tmp/data.txt" #\r)
  (print (or-else (read-line f) "EOF")))
```

Макрос раскрывается в `catch-error` вокруг тела, поэтому хэндл закрывается и при
нормальном возврате, и при `throw`. Чтение буферизовано, `close-file`
идемпотентно, а незакрытые хэндлы закрываются при teardown.

## 5.7 Почему это подходит для ML

Типичный цикл обучения держит веса в `world`, а активации — в scratch/pool:

```lisp
(defvar epoch :fixnum 0)
(defvar lr :flonum 0.01)

(while (< epoch 200)
  (grad! (loss c xs ys))
  (tset! c 0 (- (tref c 0) (* lr (tref (grad-of c) 0))))
  (setq epoch (+ epoch 1)))
```

Каждая итерация `while` начинается с mark и заканчивается `resetScratch`:
промежуточные тензоры и cons-ячейки возвращаются, вес остаётся в `world`, а
grad параметра — в его `Tensor.grad`. Память на итерацию — постоянного порядка,
без GC-пауз и без ручного освобождения. Буферы графа переиспользуются через
`TensorBufferPool` точного размера.
