# Глава 5. Модель памяти: HibLin (гибридная линейная аллокация)

Модель памяти Qualisp называется **HibLin** (Hybrid Linear) — и это главная идея, отличающая Qualisp
и от Python (GC), и от Rust (borrow checker), и от C (malloc/free). Данные по умолчанию
**одноразовые** и живут ровно в том scope, где созданы; при выходе из scope они возвращаются
в пулы. Никакого GC, ни borrow-checker, ни ручного free.

При этом структурные данные (S-выражения, cons-ячейки, глобальные значения) живут **под подсчётом
ссылок**: они шарятся между местами, которые их используют, и умирают, когда последний
владелец их отпустил. Подсчёт ссылок действует вне пула тензорных буферов — там, где у
значения один владелец, ссылаться больше некому.

## 5.1 Аналогия с черновиком

Решая пример в столбик на бумаге, вы пишете исходные числа на черновике, промежуточный
результат — тоже на черновике, и переписываете в чистовик только ответ. Черновик
выбрасывается.

HibLin работает так же: данные по умолчанию **одноразовые** (disposable). Сохранить можно
только явным **переписыванием** — `defvar` (в «тетрадь»), а все промежуточные значения
живут в текущем scope и исчезают вместе с ним.

С чисто числовыми примерами аналогия на этом исчерпана. Если один и тот же результат
нужен в трёх местах, вы не заводите три копии на столе — вы заводите **одну карточку и
счётчик читателей**: пока читателей не ноль, карточка жива. Это и есть подсчёт ссылок:
он появляется не как отдельная сущность, а потому, что «одна карточка на всех» дешевле
копирования, и потому, что у черновика нет срока годности, а у карточки есть читатели.

> 🐍 **Python-аналогия.** В Python всё живёт в heap, и garbage collector периодически
> находит и освобождает недостижимые объекты. Вы думаете о владении редко — платя GC-паузами
> и накладными расходами. В Qualisp освобождение детерминированное и мгновенное: scope
> кончился — тензорные буферы вернулись в пул, cons-ячейки тоже; а структура, на которую
> кто-то ещё ссылается, живёт ровно до последнего владельца.

## 5.2 Три правила

| Правило | Что означает | Аналогия |
|---|---|---|
| 1. Всё disposable | Данные живут в текущем scope, при выходе возвращаются в пул | Черновик |
| 2. Explicit save | `defvar`/`setq` глобального кладёт значение в stable-память | Переписал в тетрадь |
| 3. RC вне тензоров | Структурные данные (S-выражения, cons-, stable-ячейки) живут под подсчётом ссылок и **шарятся**; память тензоров (TensorBufferPool) — без RC: один владелец, точный размер, глубокая копия | Документы в архиве хранятся с числом читателей; деталь на конвейере — ровно одна |

Правило 3 — не исключение из модели, а её вторая половина. «Одноразовое» относится к
владению по умолчанию; когда значение явно сохранено и на него ссылаются несколько
мест, у него появляются несколько владельцев, и владение надо посчитать.

## 5.3 Три пула HibLin

В HibLin **три специализированных пула**, каждый для своего типа данных. Подробности реализации — в `src/core/`.

| Пул | Файл | Назначение | Размер объектов | Переиспользование |
|---|---|---|---|---|
| **TensorBufferPool** | `tensor_buffer_pool.cpp` | Тензоры, активации, градиенты | Точный размер (0% перерасхода) | Free list по точному размеру + кэш по (shape, dtype) |
| **ConsCellPool** | `cons_cell_pool.cpp` | S-выражения, cons-ячейки (списки, формы) | Фиксированный (sizeof(SExpr)) | Свободный список (free list), блоки ячеек через `platform::page_alloc` |
| **StableMemory** | `stable_memory.cpp` + `Scope(stable=true)` | Веса моделей, глобальные структуры (`defvar`/`defun`) | Любой | Не переиспользуется; живёт до завершения программы |

> 🐍 **Python-аналогия.** Это как если бы PyTorch держал три цеха: один — только
> для тензорных буферов (точно по размеру, без мусора), второй — только для маленьких
> списков, третий — для весов модели, которые не трогает до конца. Ни один байт не
> пропадает, и ничто не «собирается» через раз.

### Детали TensorBufferPool

- **Exact-size**: ключ в `unordered_map` — точный размер в байтах. Никаких size-class'ов, никакого округления.
- **Acquire** (`TensorBufferPool::acquire(bytes)`): если в bucket'е нужного размера есть свободный буфер — pop O(1); иначе выделение нового блока.
- **Release** (`TensorBufferPool::release(ptr, size)`): буфер возвращается в bucket своего размера. Пул ограничен по объёму; при переполнении лишние буферы уходят системе, а не копятся в процессе.
- **Thread-safe**: `std::mutex` вокруг `unordered_map`.

Это полностью соответствует идее HibLin, описанной в `ARCHITECTURE.md`: точное выделение, без арен и size-class'ов.

### Детали ConsCellPool

Пул cons-ячеек работает как free list: `acquire()` забирает ячейку из списка свободных
за O(1), `free()` возвращает её туда же. Блоки растут по мере необходимости; при
`clear()` все блоки возвращаются системе через `platform::page_free`.

### Детали StableMemory и Scope

`Scope` (`src/core/scope.hpp`) — единица времени жизни с двумя режимами:

| Режим | Не-SExpr-аллокации | Cons-ячейки |
|---|---|---|
| `stable=true` (root/immortal) | идут в StableMemory (обычный `new`), живут до teardown scope | из ConsCellPool; умирают по счётчику ссылок |
| `stable=false` (scratch) | bump-блоки (`DEFAULT_BLOCK_SIZE = 16 МБ`), `Scope::reset()` сбрасывает | из ConsCellPool, возвращаются при reset/restore |

`Scope::track_external(ptr, bytes)` — учёт внешних (тензорных) буферов: при reset/restore они возвращаются в TensorBufferPool через `release(ptr, bytes)`.

`Scope::promote(val)` — мост между мирами: значение копируется в родительский scope (`clone_to(*parent_)`) — глубокое копирование.

### Два мира (владеет Interpreter)

`Interpreter` держит два scope:

- `root_arena_` (stable=true) — для `defvar`/`defun`/`defmacro`/`defrule`/`define-compiler-macro`/plist/весов модели. Ячейка умирает, когда **последний владелец её отпустил**; досрочная явная смерть — `(clear sym …)`, `(drop-model m)`, перепись биндинга.
- `scratch_arena_` (stable=false) — дочерний от root; все disposable значения. Живёт один scope, умирает целиком на границе формы (оптовый возврат в пулы).

Доступы: `Interpreter::scope()` (scratch), `Interpreter::stable_scope()` (root). Примитив `SCOPE-STATS` (`prim_scope_stats`) возвращает `allocated_bytes()` текущего scope.

REPL после каждого выражения вызывает `Interpreter::reset_scratch()` — disposable-область сбрасывается, буферы тензоров и cons-ячейки возвращаются в пулы.

## 5.4 Два мира данных

```text
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  SCRATCH (disposable)        │     │  STABLE (persistent)        │
│                              │     │                              │
│  let-биндинги                │     │  defvar/defun/defmacro       │
│  промежуточные SExpr         │     │  глобальные биндинги         │
│  временные списки            │     │  код-как-данные:             │
│  локальные замыкания         │     │    макросы, правила          │
│  forward/backward тензоры    │     │  plist-данные                │
│                              │     │  веса модели                 │
│                              │     │                              │
│  Живёт 1 scope.              │     │  Живёт всю программу.        │
│  Выход — всё в пулы.         │     │  Смерть — по счётчику ссылок.│
└─────────────────────────────┘     └─────────────────────────────┘
```

| Мост между мирами | `defvar`/`setq` глобального — значение **глубоко клонируется** в стабильный мир (`Scope::promote`). Тензор — новый буфер в StableMemory; список — новые ячейки; ни одна ссылка не переходит из scratch в stable. Значение, переживающее цикл, промоутится и дальше **шаряется под RC** (см. §5.5). |

Клонирование — мост по умолчанию, но не единственный: значение, **уже стабильное**,
может быть разделено под счётчиком ссылок без копии. Это допустимо ровно потому, что
стабильная ячейка достигает только стабильные ячейки или бессмертные и никогда — scratch;
иначе разделение без копии было бы оптимизацией наугад.

### `reset_scratch`: «запечатывание» графа

Форма, которая не закрыла autograd-граф, не должна оставлять после себя висящие
указатели. Поэтому `reset_scratch` «запечатывает» незакрытые графы:

1. Если форма верхнего уровня завершилась без `GRAD!`, и какие-то tape-узлы ссылаются на scratch-тензоры, эти тензоры **один раз клонируются в stable** (per-tensor — не на каждый узел).
2. Рёбра `result` tape-узлов переписываются на stable-копии.
3. Обучающие циклы ничего не платят — tape пуст после каждого `GRAD!`, и `reset_scratch` идёт по пустому tape.

Смысл: `defvar` промежуточного тензора и `grad!` в **следующей** форме детерминированно
работают в Release и под ASan. Подробности — в гл. 7 (раздел «Контракт gradient tape»).

### Времена жизни градиентов

Контракт смерти `Tensor::grad` строгий: буферы градиентов аллоцируются в scratch-регионе
вызова `backward()` и живут до его смерти (restore итерации `while`, сброс формы). При
входе в `backward()` на каждый нодовый тензор регистрируется guard (`Scope::track_dtor` +
`Tensor::clear_grad`): при смерти региона поле честно обнуляется, следующая итерация
аллоцирует свежий буфер вместо `add_inplace` в чужую, уже переиспользованную память
пула. Guard'ы срабатывают LIFO по порядку аллокаций — старый guard не может затереть живой
новый градиент; `seal()` не копирует на stable-клон grad умирающего региона.

Контракт `GRAD-OF` при этом не меняется (нули при отсутствии grad — на этом держатся
NS guilt-тесты), но истёкший grad — настоящий null, а не указатель в переиспользованный
пул.

## 5.5 Контракты владения

Ниже — действующий контракт, без истории его выработки. Он держится на четырёх идеях:
у ячейки есть счётчик ссылок; поле, куда кладут значение, само берёт ссылку; смерть
последнего владельца тянет за собой каскад; владельцем ячейки является выделивший её
scope.

### 5.5.1 Два контракта: структура под RC, тензоры — под пулом

| | Структурные данные | Данные тензоров |
|---|---|---|
| Где живут | `ConsCellPool` + `StableMemory` | `TensorBufferPool` (exact-size) |
| Сколько владельцев | сколько угодно, считается счётчиком | ровно один |
| Как делится | ссылка (`stable_ref`) | глубокая копия |
| Как умирает | счётчик упал в ноль → каскад | возврат в пул по scope |

RC к тензорным буферам не применяется сознательно: у тензора нет «второго держателя»,
которого можно было бы отследить, а буфер должен лежать по точному размеру. Второй
владелец такого буфера означал бы либо алиас (view), либо копию — а оба запрещены
(см. §5.5.8).

### 5.5.2 Бессмертие — флаг в данных

Бессмертие выражено **флагом в самой ячейке**, а не исключением «по идентичности» и не
записью в отдельном реестре владельцев. У ячейки есть счётчик ссылок и бит бессмертия.

`nil` бессмертен: он стоит cdr каждого хвоста списка и возвращается каждым `nil()` —
освобождать его нельзя, иначе пул отдаст адрес единственной бессмертной ячейки как
свежую. Всё остальное смертно и умирает по счётчику.

### 5.5.3 Поле берёт ссылку

Правило: **структурное поле само берёт ссылку** на значение, которое в него кладут.
Это касается и cons-пары, и захвата замыкания, и записи в реестр (plist, слоты
структур, реестры fusion), и back-ref'ов декодера образов.

Следствие — в коде нет компенсирующих обходов: ни «обхода структуры с добиранием
ссылок», ни отдельного аудита «все ли места взяли ссылку». Место, где значение
кладётся, и есть место, где ссылка берётся.

Первую ссылку отдаёт создатель ячейки: при установке значения в поле создатель
передаёт ячейке «семя» владельца (creator-seed). Счётчик после этого честный —
двойных и фантомных клеймов нет: ровно столько, сколько владельцев.

### 5.5.4 Каскад смерти

Смерть последнего владельца ячейки тянет за собой её содержимое: значения, лежащие в
умирающей ячейке, освобождаются вместе с ней. Каскад **итеративный** (worklist), а не
рекурсивный: на пути смерти нет стека, поэтому глубина структуры не ограничивает
кадры. Строковые байты возвращаются системе, HLO-программа освобождает свою страницу
и артефакты, тензор снимается с трекинга.

### 5.5.5 Владелец ячейки — её scope

Ячейка принадлежит scope, который её выделил, и не должна использоваться после его
restore/reset: scope освобождает всё, что выделил, при восстановлении. «Владелец
ячейки — её scope» — это и есть правило, из которого следует всё остальное: у
scratch-ячеек владелец один и короткоживущий, у stable-ячеек срок жизни задаёт
счётчик ссылок, а scope-владелец (root) живёт до конца программы.

### 5.5.6 Прямые `malloc`/`free` для данных тензоров

`TensorBufferPool` остаётся путём по умолчанию — он даёт exact-size, автоматический
возврат по scope и предсказуемый учёт. Но когда пул не выражает нужное (буфер
переживает свой скоуп, переиспользуется как scratch, требуется освобождение в
произвольной точке), **разрешён прямой `malloc`/`calloc`/`realloc`/`free`** для данных
тензоров.

Что обязано сопровождать такое выделение:

- **кто выделил — тот и освобождает**, и точка `free` пишется **рядом с местом
  выделения**, а не «когда-нибудь при разборке»;
- на такой буфер **не распространяются** exact-size учёт пула и счётчики
  `(mem-report)` — это надо помнить при разборе утечек;
- новые сырые выделения обязаны приходить с тестом: двойное освобождение и
  use-after-free в этом пути структурно возможны, и ловит их только ASan.

### 5.5.7 cons-ячейки — только через `ConsCellPool`

Прямое выделение cons-ячейки в обход пула выпадает из всех трёх механизмов сразу:
RC-контракта, worklist-каскада и счётчиков `(mem-report)`. Поэтому cons-ячейки
выделяются **только** через `ConsCellPool` — это не оптимизация, а условие, при
котором контракт владения вообще имеет силу.

### 5.5.8 У тензоров нет view/alias

`reshape` и `transpose` — **глубокая копия**. Тензорных «представлений» (view),
перекрывающих один буфер, в языке нет: у данных тензоров один владелец, и второй
владелец означал бы ровно то, чего RC-пул не умеет отслеживать.

Правило держится не на проверке, а на устройстве: второй путь выделения заголовка
тензора (`Tensor::detach`) удалён, так что взять буфер «вторым хозяином» просто
нечем. Побочный эффект — заметный: пока источник живёт дольше результата, view и
глубокая копия неразличимы (значения те же, буфер один), и наблюдаемая разница
появляется только тогда, когда источник умирает раньше результата.

### 5.5.9 `(mem-report)` и проверочный контур

`(mem-report)` возвращает alist со счётчиками — это наблюдаемость смерти без обхода
мира:

```lisp
(print (mem-report))
;; → (("names" . 0) ("payloads" . 0) ("progs" . 0) ("tensors" . 0)
;;     ("shared" . 0) ("stable-bytes" . 124912) ("scratch-bytes" . 3922)
;;     ("scratch-cells" . 26003) ("stable-cells" . 26850)
;;     ("stable-cells-released" . 23775) ("cells-acquired" . 76628)
;;     ("cell-pool-cells" . 65536) ("immortal-cells" . 1) ("jit-observations" . 0)
;;     ("jit-pages" . 0) ("buffers-released" . 0) ("progs-released" . 0))
```

Ключи: `names`/`payloads`/`progs`/`tensors`/`shared` — реестры и их содержимое,
`stable-bytes`/`scratch-bytes` — байты арен, `scratch-cells`/`stable-cells` — живые
ячейки, `stable-cells-released` — освобождённые ячейки, `cells-acquired` — сколько
ячеек пул выдал за всё время, `cell-pool-cells` — сколько ячеек в пуле (ёмкость
блока), `immortal-cells` — бессмертные ячейки (всегда одна — `nil`),
`jit-observations` — наблюдения типов для JIT, `jit-pages` — живые нативные
страницы JIT (падает со смертью последней исполняющей их обёртки, гл. 20),
`buffers-released` и `progs-released` — счётчики death-hook'ов (освобождённые
тензорные буферы и HLO-программы).

Проверяемость контракта обеспечивают два гейта:

- **poison-гейт.** `QUALISP_RC_POISON=1` отравляет освобождённые ячейки `ConsCellPool`
  (и приборы для тензорных буферов и heap-заголовков): прогон, который читает
  освобождённую ячейку или освобождает её дважды, падает на месте, а не «иногда».
  Отдельный poison-гейт прогоняет весь корпус.
- **ASan-гейт.** Сборка с `detect_leaks=1` ищет утечки, а не только use-after-free;
  рецепт — `tools/asan_gate.sh`. Без `ulimit -s unlimited` гейт даёт ложные
  stack-overflow: кадры ASan втрое крупнее, а `macroexpand_1` рекурсивен по
  вложенности формы. Гейт собирает **все** падения за прогон и падает в конце, а не
  на первом файле.

### 5.5.10 Открытое ограничение: per-value RC для scratch-ячеек

Счётчик есть у **каждой** ячейки, включая scratch. Но полноценное владение scratch-ячейками
пока не доведено: оптовый возврат scope не умеет освобождать поячеечно, поэтому per-value RC
для scratch — впереди. Это честное ограничение, а не баг: оно названо здесь, чтобы его не
искали в других местах.

> 🐍 В Python аналог — `weakref` плюс ручной `del` в нужных местах; здесь освобождение не
> «произойдёт когда-нибудь», а имеет проверяемый контракт: счётчик ссылок в самой ячейке,
> poison-гейт и ASan-гейт, которые ловят нарушение сразу.

## 5.6 Операции и их владение

| Операция | Входы | Выход | Где живёт |
|---|---|---|---|
| `(MATMUL x w)` | `x`, `w` читаются (не потребляются) | новый тензор | scratch (TensorBufferPool) |
| `(defvar w val)` | `val` нетронут | копия `val` (clone_to) | stable (root scope) |
| `(setq w val)` глобальной | — | значение промотится в stable и дальше шарётся под RC | stable |
| `(setq x val)` локальной | — | — | обновляет `x` на месте в scratch |
| `(defun f ...)` | — | — | замыкание → root scope (через `root_arena_`) |
| `(defmacro m ...)` | — | — | замыкание → root scope |
| `(defrule name (vars) (when ...) (assert ...))` | — | — | правило → root scope (clone_to) |
| `(assert-fact ...)` | — | — | факт → root scope |
| `return result` (через `progn`/let) | — | — | auto-clone в scope-родителя при `promote` |

Техническая деталь: тензор в scratch живёт в TensorBufferPool; при выходе из scope
буфер возвращается в точный free list — следующий тензор того же размера возьмёт его
за O(1), без системного аллокатора.

## 5.7 Почему это идеально для ML

Типичный цикл обучения:

```lisp
(while (< i 1000)
  (let ((pred (matmul! x w)))       ; pred ~1 МБ на scratch
    (let ((loss (mse! pred y)))     ; loss ~1 байт, pred потреблён
      (grad! loss)                  ; градиенты на scratch
      (sgd-step w 0.01)             ; w обновлён на месте (stable)
      (setq i (+ i 1)))))
```

1000 итераций используют **одни и те же ~1 МБ** scratch-памяти: без единого free,
без GC-пауз, без роста потребления. Каждая итерация while создаёт новый scope
через `checkpoint()/restore()` (см. `Scope::checkpoint()`, `Scope::restore()`); на
выходе итерации буферы возвращаются в пулы. Результат тела цикла живёт в паре
ping-pong scratch-скоупов — максимум две живые копии, — и в root продвигается один
раз на выходе; те же семантики возврата, O(1) памяти на итерацию. Контракт
возвращаемого значения зафиксирован в `tests/while_semantics.qlsp`.

Утечки памяти в ядре ловит soak-харнесс (`tests/memory_soak.qlsp` + `bench/leak_watch.py`):
churn-циклы (cons, строки, eager-тензоры, autograd, HLO, while) с VmRSS-чекпоинтами
через `/proc`.
