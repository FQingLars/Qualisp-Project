# Глава 5. Модель памяти: HibLin (гибридная линейная аллокация)

Модель памяти Qualisp называется **HibLin** (Hybrid Linear) — и это главная идея, отличающая Qualisp
и от Python (GC), и от Rust (borrow checker), и от C (malloc/free). Данные по умолчанию
**одноразовые** и живут в scope'е своего хранилища: промежуточные значения умирают на конце
своего scope'а и возвращаются в пулы, а результат живёт там, где его ждут. Никакого GC, ни
borrow-checker, ни ручного free.

При этом стабильные структурные данные (S-выражения, cons-ячейки, глобальные значения) живут
**под подсчётом ссылок**: они шарятся между местами, которые их используют, и умирают, когда
последний владелец их отпустил. Подсчёт ссылок действует в stable-мире — там, где сроки жизни
не-LIFO; scratch-мир живёт как стек, и счётчиков там нет.

## 5.1 Аналогия с черновиком

Решая пример в столбик на бумаге, вы пишете исходные числа на черновике, промежуточный
результат — тоже на черновике, и переписываете в чистовик только ответ. Черновик
выбрасывается.

HibLin работает так же: данные по умолчанию **одноразовые** (disposable). Сохранить можно
только явным **переписыванием** — `defvar` (в «тетрадь»), а все промежуточные значения
живут в текущем scope и исчезают вместе с ним.

С чисто числовыми примерами аналогия на этом исчерпана. Если один и тот же результат
нужен в трёх местах, вы не заводите три копии на столе — вы заводите **одну карточку и
счётчик читателей**: пока читателей не ноль, карточка жива. Это и есть подсчёт ссылок:
он появляется не как отдельная сущность, а потому, что «одна карточка на всех» дешевле
копирования, и потому, что у черновика нет срока годности, а у карточки есть читатели.

> 🐍 **Python-аналогия.** В Python всё живёт в heap, и garbage collector периодически
> находит и освобождает недостижимые объекты. Вы думаете о владении редко — платя GC-паузами
> и накладными расходами. В Qualisp освобождение детерминированное и мгновенное: scope
> кончился — тензорные буферы вернулись в пул, cons-ячейки тоже; а структура, на которую
> кто-то ещё ссылается, живёт ровно до последнего владельца.

## 5.2 Три правила

Модель держится на трёх правилах — это и есть действующий контракт (механика — в §5.5):

| Правило | Что означает | Аналогия |
|---|---|---|
| 1. Дерево scope'ов = дерево вычислений | Каждый вызов функции (и существующие loop-точки `while`/TCO) получает дочерний scope своего вызывающего; откат scope'а — **одна запись** | Каждый шаг решения в столбик — своя строка черновика |
| 2. Значение живёт в scope'е своего хранилища | Промежуточные данные умирают на конце своего scope'а; результат и записываемое значение, чья судьба длиннее, переезжают в scope хранилища; def-формы (`defun`/`defvar`/`defstruct`/`defmacro`/…) пишут в stable **всегда** | Черновик и тетрадь: переписал — и черновик больше не нужен |
| 3. Побег региона — явное событие | Регион не откатывается (переходит родителю), если результат указывает в него ИЛИ в нём есть клетка с чужим владельцем | Запись, переписанная в чистовик, не выбрасывается с черновиком |

Правило 3 несёт **осознанную семантику (гистерезис)**: рекурсия, строящая большой результат
(списко-образующая), не откатывает регион — память O(аллокаций), копий нет; мусорная рекурсия
чинится полностью: O(глубина) вместо O(всех аллокаций формы).

Вторая половина модели — два режима жизни ячеек. Скретч-ячейки не несут счётчика и умирают
**только откатом** scope'а; счётчик ссылок живёт в stable — там, где сроки жизни не-LIFO:
`defvar`/`defun`, веса модели, программы, реестры. Разделение значений — не исключение из
модели: когда сохранённое значение используется в нескольких местах, владение считается
(§5.5.2).

## 5.3 Три пула HibLin

В HibLin **три специализированных пула**, каждый для своего типа данных. Подробности реализации — в `src/core/`.

| Пул | Файл | Назначение | Размер объектов | Переиспользование |
|---|---|---|---|---|
| **TensorBufferPool** | `tensor_buffer_pool.cpp` | Тензоры, активации, градиенты | Точный размер (0% перерасхода) | Free list по точному размеру + кэш по (shape, dtype) |
| **ConsCellPool** | `cons_cell_pool.cpp` | S-выражения, cons-ячейки (списки, формы) | Фиксированный (sizeof(SExpr)) | Свободный список (free list), блоки ячеек через `platform::page_alloc` |
| **StableMemory** | `stable_memory.cpp` + `Scope(stable=true)` | Веса моделей, глобальные структуры (`defvar`/`defun`) | Любой | Не переиспользуется; живёт до завершения программы |

> 🐍 **Python-аналогия.** Это как если бы PyTorch держал три цеха: один — только
> для тензорных буферов (точно по размеру, без мусора), второй — только для маленьких
> списков, третий — для весов модели, которые не трогает до конца. Ни один байт не
> пропадает, и ничто не «собирается» через раз.

### Детали TensorBufferPool

- **Exact-size**: ключ в `unordered_map` — точный размер в байтах. Никаких size-class'ов, никакого округления.
- **Acquire** (`TensorBufferPool::acquire(bytes)`): если в bucket'е нужного размера есть свободный буфер — pop O(1); иначе выделение нового блока.
- **Release** (`TensorBufferPool::release(ptr, size)`): буфер возвращается в bucket своего размера. Пул ограничен по объёму; при переполнении лишние буферы уходят системе, а не копятся в процессе.
- **Thread-safe**: `std::mutex` вокруг `unordered_map`.

Это полностью соответствует идее HibLin, описанной в `ARCHITECTURE.md`: точное выделение, без арен и size-class'ов.

### Детали ConsCellPool

Пул cons-ячеек работает как free list: `acquire()` забирает ячейку из списка свободных
за O(1), `free()` возвращает её туда же. Блоки растут по мере необходимости; при
`clear()` все блоки возвращаются системе через `platform::page_free`.

### Детали StableMemory и Scope

`Scope` (`src/core/scope.hpp`) — единица времени жизни с двумя режимами:

| Режим | Не-SExpr-аллокации | Cons-ячейки |
|---|---|---|
| `stable=true` (root/immortal) | идут в StableMemory (обычный `new`), живут до teardown scope | из ConsCellPool; умирают по счётчику ссылок |
| `stable=false` (scratch) | bump-блоки (`DEFAULT_BLOCK_SIZE = 16 МБ`), `Scope::reset()` сбрасывает | из ConsCellPool, возвращаются при reset/restore |

Payload независим от ячеек (§5.5.6): тензорные записи принадлежат объекту и ретаются его
деструктором, поэтому reset/restore scope возвращает в пулы ячейки и арены, а данные тензоров
живут по владению объекта.

Мост между мирами — промоут при записи (`Scope::promote`, `clone_to`): молодое значение
клонируется в хранилище, стабильное — шарится.

### Два мира (владеет Interpreter)

`Interpreter` держит два scope:

- `root_arena_` (stable=true) — для `defvar`/`defun`/`defmacro`/`defrule`/`define-compiler-macro`/plist/весов модели. Ячейка умирает, когда **последний владелец её отпустил**; досрочная явная смерть — `(clear sym …)`, `(drop-model m)`, перепись биндинга.
- `scratch_arena_` (stable=false) — дочерний от root; все disposable значения. Живёт один scope, умирает целиком на границе формы (оптовый возврат в пулы).

Доступы: `Interpreter::scope()` (scratch), `Interpreter::stable_scope()` (root). Примитив `SCOPE-STATS` (`prim_scope_stats`) возвращает `allocated_bytes()` текущего scope.

REPL после каждого выражения вызывает `Interpreter::reset_scratch()` — disposable-область сбрасывается, буферы тензоров и cons-ячейки возвращаются в пулы.

## 5.4 Два мира данных

```text
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  SCRATCH (disposable)        │     │  STABLE (persistent)        │
│                              │     │                              │
│  let-биндинги                │     │  defvar/defun/defmacro       │
│  промежуточные SExpr         │     │  глобальные биндинги         │
│  временные списки            │     │  код-как-данные:             │
│  локальные замыкания         │     │    макросы, правила          │
│  forward/backward тензоры    │     │  plist-данные                │
│                              │     │  веса модели                 │
│                              │     │                              │
│  Живут в scope'е создания.   │     │  Живёт всю программу.        │
│  Выход — откат в пулы.       │     │  Смерть — по счётчику ссылок.│
└─────────────────────────────┘     └─────────────────────────────┘
```

| Мост между мирами | Запись молодого значения в более старое хранилище **промоутит** значение: та же ячейка, ноль копий, возрастной тест — по штампам (§5.5.5). При связывании имени (`defvar`/`setq` глобального) скретч-значение клонируется в stable — тензор получает новый буфер, список — новые ячейки, а стабильное значение **делится** (alias: одно значение под двумя именами, включая cons-хвосты) и дальше живёт под RC. Отдельный мост — захват замыканием: пара биндинга промоутится в stable целиком, без копий (§5.5.5). |

Правило корня: stable-хранилище не держит скретч-ячейку — «ссылка не переживает свой root»
выполняется по построению, а не проверкой. Поэтому при связывании имени молодое значение
переезжает в stable копией, а стабильное делится без копии; запись в поле или слот
промоутит значение на месте (та же ячейка, ноль копий). Стабильная ячейка достигает только
стабильные ячейки или бессмертные и никогда — scratch.

### `reset_scratch`: «запечатывание» графа

Форма, которая не закрыла autograd-граф, не должна оставлять после себя висящие
указатели. Поэтому `reset_scratch` «запечатывает» незакрытые графы:

1. Если форма верхнего уровня завершилась без `GRAD!`, и какие-то tape-узлы ссылаются на scratch-тензоры, эти тензоры **один раз клонируются в stable** (per-tensor — не на каждый узел).
2. Рёбра `result` tape-узлов переписываются на stable-копии.
3. Обучающие циклы ничего не платят — tape пуст после каждого `GRAD!`, и `reset_scratch` идёт по пустому tape.

Смысл: `defvar` промежуточного тензора и `grad!` в **следующей** форме детерминированно
работают в Release и под ASan. Подробности — в гл. 7 (раздел «Контракт gradient tape»).

### Времена жизни градиентов

Контракт смерти `Tensor::grad` строгий: буферы градиентов аллоцируются в scratch-регионе
вызова `backward()` и живут до его смерти (restore итерации `while`, сброс формы). При
входе в `backward()` на каждый нодовый тензор регистрируется guard (`Scope::track_dtor` +
`Tensor::clear_grad`): при смерти региона поле честно обнуляется, следующая итерация
аллоцирует свежий буфер вместо `add_inplace` в чужую, уже переиспользованную память
пула. Guard'ы срабатывают LIFO по порядку аллокаций — старый guard не может затереть живой
новый градиент; `seal()` не копирует на stable-клон grad умирающего региона.

Контракт `GRAD-OF` при этом не меняется (нули при отсутствии grad — на этом держатся
NS guilt-тесты), но истёкший grad — настоящий null, а не указатель в переиспользованный
пул.

## 5.5 Контракты владения: scope-дерево, правило корня, конвенция передачи

Ниже — действующий контракт. Три правила модели (§5.2) обеспечиваются тремя механизмами:
**scope-деревом** — как живут и откатываются scope'ы; **правилом корня** — почему «ссылка не
переживает свой root» выполняется по построению; **конвенцией передачи владения** — как
единица владельца переходит от создателя к держателю.

### 5.5.1 Scope-дерево = дерево вычислений

Каждый вызов функции (и существующие loop-точки `while`/TCO) получает дочерний scope своего
вызывающего. Граница scope'а — метка `offset + cells_.size() + epoch` в списке ячеек, откат —
**одна запись**: стоимость возврата не зависит от числа созданных ячеек. Scope — стековый
RAII-объект, его деструктор делает restore; throw из глубины вызовов откатывает сам, никаких
ручных меток в обработчиках ошибок.

На выходе из scope действует **правило побега региона** (правило 3): регион не откатывается,
а переходит родителю, если результат указывает в него ИЛИ в нём есть клетка с чужим
владельцем. Это осознанная семантика (гистерезис): рекурсия, строящая большой результат
(списко-образующая), не откатывает регион — память O(аллокаций), копий нет; мусорная рекурсия
чинится полностью: O(глубина) вместо O(всех аллокаций формы).

### 5.5.2 Скретч = стек, RC — только в stable

Скретч-ячейки **не несут счётчика**: их смерть — только откатом scope'а (`scratch_death`):
единицы полей-хранилищ отпускаются, выполняется payload-деструктор, ячейка возвращается в пул.
Пер-ячеечного free в скретче нет.

- RC живёт только в **stable** — там, где сроки жизни не-LIFO: `defvar`/`defun`, веса модели,
  программы, реестры. Смерть stable-ячейки — RC-каскад (§5.5.4).
- Бессмертие выражено **флагом в самой ячейке**, а не исключением «по идентичности» и не
  записью в отдельном реестре владельцев. `nil` бессмертен: он стоит cdr каждого хвоста
  списка и возвращается каждым `nil()` — освобождать его нельзя, иначе пул отдаст адрес
  единственной бессмертной ячейки как свежую.
- Живая unmanaged-ячейка всегда несёт birth-единицу (§5.5.3); релиз при `rc == 0` — тихий
  no-op (мёртвый адрес), при `rc == 1` — громкий яд.
- Единый маркер мёртвой ячейки — `refs_ == 0` на всех путях смерти (откат, RC-каскад, poison).

| | Стабильные структуры | Данные тензоров |
|---|---|---|
| Где живут | `ConsCellPool` + `StableMemory` | `TensorBufferPool` (exact-size) либо прямой `malloc` |
| Сколько владельцев | сколько угодно, считается счётчиком | ровно один |
| Как делится | запись шарится (alias); «разделение» — явный `hold` | глубокая копия |
| Как умирает | счётчик упал в ноль → каскад | деструктор тензора (payload) |

RC к тензорным буферам не применяется сознательно: у тензора нет «второго держателя»,
которого можно было бы отследить, а буфер должен лежать по точному размеру. Второй
**writable**-владелец такого буфера означал бы алиас, который можно писать, — он запрещён;
read-only окна (§5.5.8) — явный алиас только для чтения, и их владелец держится счётчиком.

### 5.5.3 Конвенция передачи владения

Ячейка рождается с **birth-единицей**, которая **передаётся** первому держателю: поле, куда
кладут значение, берёт единицу без лишнего `stable_ref` — ячейка помечается меткой
`kHandedBit` (birth-единица потреблена держателем). Перезапись поля = освобождение старого
значения. «Разделение» — когда у значения появляется второй держатель — явный `hold` в точке
деления.

Конвенция покрывает все места, куда кладётся значение: cons-пару, захват замыкания, записи в
реестры (plist, слоты структур, реестры fusion), back-ref'ы декодера образов. Одно соглашение
вместо россыпи точек-хэндоффов: в коде нет ни «обхода структуры с добиранием ссылок», ни
отдельного аудита «все ли места взяли ссылку» — место, где значение кладётся, и есть место,
где единица передаётся. Sweep scope'а отдаёт только неотданное: помеченная `kHandedBit`
ячейка принадлежит держателю и откатом не убивается.

### 5.5.4 Каскад смерти (stable)

Смерть последнего владельца stable-ячейки тянет за собой её содержимое: значения, лежащие в
умирающей ячейке, освобождаются вместе с ней. Каскад **итеративный** (worklist), а не
рекурсивный: на пути смерти нет стека, поэтому глубина структуры не ограничивает кадры.
Строковые байты возвращаются системе, HLO-программа освобождает свою страницу и артефакты,
тензор разрушается единственным разрушителем (§5.5.6). Scratch-ячейки каскадом не умирают —
их смерть только откатом (§5.5.2).

### 5.5.5 Правило корня и правило записи

Правило 2 («значение живёт в scope'е своего хранилища») держится на **правиле корня**:
stable-хранилище не держит скретч-ячейку — «ссылка не переживает свой root» выполняется по
построению, а не проверкой. Промежуточные данные умирают на конце своего scope'а; результат
и записываемое значение, чья судьба длиннее, переезжают в scope хранилища мостами: авто-клон
результата, promote при записи, промоут пары при захвате. def-формы (`defun`/`defvar`/
`defstruct`/`defmacro`/…) пишут в stable **всегда** — из любой глубины вызовов.

- **Захват замыканием = явный промоут пары биндинга** в stable: та же ячейка, ноль копий,
  значение общее (EQ-тождество, `m`/`v`/grad шарятся), мутации видны кадру и всем замыканиям
  на биндинге.
- **Правило записи (`promote_for_store`): мир держателя решает.** Запись молодого значения в
  более старое хранилище — поле старой клетки, слот, сырой член интерпретатора — **промоутит
  значение на месте**: та же ячейка, ноль копий; возрастной тест — по штампам (birth-билетам).
  Запись в захваченный биндинг идёт в stable-мир пары биндинга, а не в scope пишущего кадра;
  `set-slot` промоутит значение — значение в структуре живёт по правилам хранилища.
- **`setq` глобального стабильного значения делит, а не копирует.** Это относится и к
  cons-хвостам: курсор `(setq *g* (cdr *g*))` — O(1) на шаг, стабильный хвост шарится.
  Скретч-значение по-прежнему клонируется в stable (правило 2).
- **`do_while` делит стабильный результат оборота** без копии в double-buffer: правило
  `store_value` — stable share, scratch clone.

### 5.5.6 Payload независим от ячеек

Payload не является ячейкой и живёт по владению объекта: тензорные записи принадлежат
объекту (ретайр через деструкторы), тензор — **одно выделение [заголовок | данные]** с
единственным разрушителем; struct-слоты всегда `malloc` (owned-ячейкой); байты строк всегда
`malloc`. Поэтому payload переживает откат региона независимо от ячеек и умирает ровно один
раз — и откатом, и RC-каскадом.

`TensorBufferPool` остаётся путём по умолчанию для данных тензоров — он даёт exact-size,
автоматический возврат по scope и предсказуемый учёт. Но когда пул не выражает нужное (буфер
переживает свой скоуп, переиспользуется как scratch, требуется освобождение в произвольной
точке), **разрешён прямой `malloc`/`calloc`/`realloc`/`free`** для данных тензоров.

Что обязано сопровождать такое выделение:

- **кто выделил — тот и освобождает**, и точка `free` пишется **рядом с местом
  выделения**, а не «когда-нибудь при разборке»;
- на такой буфер **не распространяются** exact-size учёт пула и счётчики
  `(mem-report)` — это надо помнить при разборе утечек;
- новые сырые выделения обязаны приходить с тестом: двойное освобождение и
  use-after-free в этом пути структурно возможны, и ловит их только ASan.

### 5.5.7 cons-ячейки — только через `ConsCellPool`

Прямое выделение cons-ячейки в обход пула выпадает из всех механизмов сразу: конвенции
передачи, откатной смерти скретча, RC-каскада stable и счётчиков `(mem-report)`. Поэтому
cons-ячейки выделяются **только** через `ConsCellPool` — это не оптимизация, а условие, при
котором контракт владения вообще имеет силу.

### 5.5.8 У тензоров нет writable view/alias

`reshape` и `transpose` — **глубокая копия**. Writable-представлений (view), перекрывающих
один буфер и позволяющих писать в него через два имени, в языке нет: writable-путь должен
был бы отследить второго держателя, а RC-пул этого не умеет.

Read-only окна есть, и у них явный контракт владения. `(T-ROWS t from len)` и
`(T-SLICE t from len)` дают **read-only алиас** над любым живым владельцем — stable или
скретч; строковые окна (`STRING-VIEW`, `STRING-REF`) устроены так же. Копий при создании
окна нет. Владелец держится счётчиком: stable-ячейка — `stable_ref`; скретч-ячейка при
создании окна **повышается** в stable (`promote_cell`), поэтому откат её области гасит
только birth-единицу, а единица окна держит владельца и буфер живыми. Поэтому окно читается
после выхода владельца из scope и после переписи имени (`setq`/`defvar`), а `TSET!` в
источник виден через окно.

- **Запись через окно отказывает**: `TSET!`, `T+=`, `T*=`, `T-RELU`, `T-SCATTER-ADD`,
  `SGD-STEP`, `ADAM-STEP`, `ADAM-SPARSE-STEP` — `require_writable` (оптимизатор не должен
  молча менять веса через read-only окно).
- **Escape в stable материализует копию**: `defvar`/`setq` глобала/`Scope::promote` делают
  из окна обычный тензор-копию, и такая копия **writable**. Поэтому `(defvar v (T-ROWS t 0 1))`
  на верхнем уровне даёт копию (её можно писать, источник не меняется), а окно, живущее в
  `let`/scratch, остаётся read-only view и отказывает `TSET!`/`T+=`.
- **Окно от окна материализуется**: промежуточная ячейка окна — скретч, второе окно берёт
  копию.
- **Клон окна** (`Tensor::viewed`) — всегда глубокая копия; это отличает окно от host-`borrowed`-тензора, где контракт хоста — делиться памятью.
- `TYPE-OF` окна — `TENSOR`; для строкового окна — `STRING`.

Единственный «алиас» на уровне значений — присваивание уже стабильного тензора
(`(setq a b)`): `a` и `b` становятся одним значением (EQ-тождество), мутации и состояние
оптимизатора (`m`/`v`) видны через оба имени. Промоут тензора из scratch, напротив, остаётся
копией.

### 5.5.9 `(mem-report)` и проверочный контур

`(mem-report)` возвращает alist со счётчиками — это наблюдаемость смерти без обхода мира.
Ключей ровно **28**, порядок фиксирован: `names`, `payloads`, `progs`, `tensors`, `shared`,
`stable-bytes`, `ns-psi`, `graph-buffer`, `graph-bytes`, `vm-alloc-bytes`, `vm-free-bytes`,
`vm-live-bytes`, `scopes-born`, `scopes-died`, `scratch-bytes`, `scratch-cells`,
`scratch-cells-live`, `scratch-cells-released`, `stable-cells`, `stable-cells-released`,
`cells-acquired`, `cell-pool-cells`, `immortal-cells`, `small-int-cache-cells`,
`jit-observations`, `jit-pages`, `buffers-released`, `progs-released`. Других ключей (в
частности, `vm-alloc`, `vm-free`, `scratch-cells-born`) нет.

```lisp
(print (mem-report))
;; → (("names" . 0) ("payloads" . 0) ("progs" . 0) ("tensors" . 0) ("shared" . 0)
;;     ("stable-bytes" . 150928) ("ns-psi" . 1) ("graph-buffer" . 16777216)
;;     ("graph-bytes" . 0) ("vm-alloc-bytes" . 4272160) ("vm-free-bytes" . 73728)
;;     ("vm-live-bytes" . 4198432) ("scopes-born" . 2) ("scopes-died" . 0)
;;     ("scratch-bytes" . 0) ("scratch-cells" . 33223) ("scratch-cells-live" . 33223)
;;     ("scratch-cells-released" . 0) ("stable-cells" . 33838)
;;     ("stable-cells-released" . 29519) ("cells-acquired" . 96580)
;;     ("cell-pool-cells" . 131072) ("immortal-cells" . 131073)
;;     ("small-int-cache-cells" . 131072) ("jit-observations" . 1) ("jit-pages" . 1)
;;     ("buffers-released" . 0) ("progs-released" . 0))
```

Ключи:

- `names`/`payloads`/`progs`/`tensors`/`shared` — реестры и их содержимое;
- `stable-bytes`/`scratch-bytes` — байты арен;
- `stable-cells`/`stable-cells-released` — живые и освобождённые stable-ячейки;
  `cells-acquired` — сколько ячеек пул выдал за всё время, `cell-pool-cells` — сколько ячеек
  в пуле (ёмкость блока), `immortal-cells` — бессмертные ячейки (`nil` и кэш малых целых,
  `small-int-cache-cells` — размер этого кэша);
- `scratch-cells` — скретч-ячеек рождено кумулятивно, `scratch-cells-released` — умерло
  откатом, `scratch-cells-live` — живые сейчас; разность «рождено − умерло == живых» —
  консервация, которую закрепляют тесты;
- `vm-alloc-bytes`/`vm-free-bytes`/`vm-live-bytes` — жизненный цикл виртуальной памяти,
  `scopes-born`/`scopes-died` — scope-дерево; счётчики `vm-*` и `scopes-*` — постоянные;
- `graph-buffer`/`graph-bytes` — бюджет пути графа: действующий бюджет и израсходовано
  (гл. 10, 14); `ns-psi` — действующий пси-коэффициент NS-графа (гл. 14);
- `jit-observations` — наблюдения типов для JIT, `jit-pages` — живые нативные страницы JIT
  (падает со смертью последней исполняющей их обёртки, гл. 20);
- `buffers-released`/`progs-released` — счётчики death-hook'ов (освобождённые тензорные
  буферы и HLO-программы).

Проверяемость контракта обеспечивают гейты и диагностика:

- **poison-гейт.** `QUALISP_RC_POISON=1` отравляет освобождённые ячейки `ConsCellPool` (и
  приборы для тензорных буферов и heap-заголовков): прогон, который читает освобождённую
  ячейку или освобождает её дважды, падает на месте, а не «иногда». Корпус гоняет
  `tools/poison_gate.sh` — crash-aware гейт яда: он проверяет exit-код, маркер успеха и
  тексты нарушений, а не только хвост вывода.
- **POOL-DUP** — детектор двойного освобождения: ловит возврат уже мёртвой ячейки в пул и
  печатает обе истории смерти. `(RC-POISON?)` отвечает, включён ли яд.
- **`QUALISP_MEM_ROOTS=1`** — обход живых корней и кольцо событий (включая кольцо
  rc-событий) для охоты за утечками: после разборки мира видны ячейки-корни без держателей
  и ссылающиеся на них, а кольцо показывает историю рождения, передачи и смерти по адресу.
- **ASan-гейт.** Сборка с `detect_leaks=1` ищет утечки, а не только use-after-free;
  рецепт — `tools/asan_gate.sh`. Без `ulimit -s unlimited` гейт даёт ложные
  stack-overflow: кадры ASan втрое крупнее, а `macroexpand_1` рекурсивен по вложенности
  формы. Гейт собирает **все** падения за прогон и падает в конце, а не на первом файле.

Под ядом RSS-пороги пропускаются: это тестовая инфраструктура, а не модель.

**Отложенные буферы тензоров** (те, что лента держала на момент смерти обёртки) дренятся
на **всех четырёх** откатах оборота — `do_while`, оба TCO-rollback, нативный loop-rollback —
после `restore` и cell-flush. Flush проверяет `tape_holds`, поэтому законно живущий между
итерациями граф не трогается; иначе backward/`GRAD-ACCUM!` в `while` копил бы буфер
градиента до конца формы.

### 5.5.10 Честные границы модели

У модели есть границы, названные здесь, чтобы их не искали в других местах:

- **Лента autograd и бектрейс живут по своим каналам.** Рёбра ленты держат сырые `Tensor*`,
  формы бектрейса — свои копии: правило корня их не покрывает автоматически, обслуживаются
  они отдельными каналами (гл. 7, §19.5).
- **Хвостовая рекурсия (TCO) клонирует результат на финальном safe-возврате** — семантика
  возврата у неё отдельная; не-хвостовая рекурсия возвращает значение без копий
  (гистерезис, §5.5.1).
- **Гистерезис — семантика, а не баг**: списко-образующая рекурсия не откатывает регион и
  потребляет O(аллокаций) памяти.
- **Окна не нарушают три правила.** Read-only окно — не writable view и не исключение из
  модели, а явный алиас только для чтения с владением по счётчику (§5.5.8); writable views
  по-прежнему нет.
- **Билет рождения — 24-битный счётчик.** Сравнение возрастов корректно переживает его
  оборот (≈16.7 млн): старое значение не выглядит «рождённым после» метки.
- **Перечень исключений модели не растёт.** Новое исключение без строки в `ARCHITECTURE.md`
  не считается обоснованным; окна в перечень не входят — это alias с явным контрактом, а не
  обход правила.

> 🐍 В Python аналог — `weakref` плюс ручной `del` в нужных местах; здесь освобождение не
> «произойдёт когда-нибудь», а имеет проверяемый контракт: счётчик ссылок в stable-ячейке,
> единый маркер мёртвой ячейки, poison-гейт и ASan-гейт, которые ловят нарушение сразу.

## 5.6 Операции и их владение

| Операция | Входы | Выход | Где живёт |
|---|---|---|---|
| `(MATMUL x w)` | `x`, `w` читаются (не потребляются) | новый тензор | scratch (TensorBufferPool) |
| `(defvar w val)` | `val` нетронут | копия `val` (clone_to) | stable (root scope) |
| `(setq w val)` глобальной | — | значение промоутится в stable (молодое — клоном, стабильное — шарится) | stable |
| `(setq x val)` локальной | — | — | обновляет `x` на месте в scratch |
| `(defun f ...)` | — | — | замыкание → root scope (через `root_arena_`) |
| `(defmacro m ...)` | — | — | замыкание → root scope |
| `(defrule name (vars) (when ...) (assert ...))` | — | — | правило → root scope (clone_to) |
| `(assert-fact ...)` | — | — | факт → root scope |
| `return result` (через `progn`/let) | — | — | auto-clone в scope-родителя при `promote` |

Техническая деталь: тензор в scratch живёт в TensorBufferPool; при выходе из scope
буфер возвращается в точный free list — следующий тензор того же размера возьмёт его
за O(1), без системного аллокатора.

## 5.7 Почему это идеально для ML

Типичный цикл обучения:

```lisp
(while (< i 1000)
  (let ((pred (matmul! x w)))       ; pred ~1 МБ на scratch
    (let ((loss (mse! pred y)))     ; loss ~1 байт, pred потреблён
      (grad! loss)                  ; градиенты на scratch
      (sgd-step w 0.01)             ; w обновлён на месте (stable)
      (setq i (+ i 1)))))
```

1000 итераций используют **одни и те же ~1 МБ** scratch-памяти: без единого free,
без GC-пауз, без роста потребления. Каждая итерация while создаёт новый scope
через `checkpoint()/restore()` (см. `Scope::checkpoint()`, `Scope::restore()`); на
выходе итерации буферы возвращаются в пулы. Результат тела цикла живёт в паре
ping-pong scratch-скоупов — максимум две живые копии, — и в root продвигается один
раз на выходе; те же семантики возврата, O(1) памяти на итерацию. Контракт
возвращаемого значения зафиксирован в `tests/while_semantics.qlsp`.

Утечки памяти в ядре ловит soak-харнесс (`tests/memory_soak.qlsp` + `bench/leak_watch.py`):
churn-циклы (cons, строки, eager-тензоры, autograd, HLO, while) с VmRSS-чекпоинтами
через `/proc`.
