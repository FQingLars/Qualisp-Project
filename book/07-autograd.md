# Глава 7. Автоградиент

В Qualisp встроен reverse-mode автоградиент через **ленту градиентов** (gradient tape) — как `torch.autograd`, но на уровне ядра языка.

## 7.1 Конвенция: операции с `!`

- **Обычные операции** (`MATMUL`, `T+`, `RELU`, …) — чистые вычисления без записи градиентов.
- **Autograd-операции** (суффикс `!`: `MATMUL!`, `T+!`, `RELU!`, …) — то же вычисление **плюс запись узла на ленту**.

> 🐍 **Python-аналогия.** В PyTorch запись на ленту управляется флагом `requires_grad` тензора. В Qualisp — выбором имени операции: `MATMUL` vs `MATMUL!`. Явно, видно в коде, ничего не «сливается» случайно.

Имена autograd-примитивов (из `src/eval/interpreter.cpp:register_primitives`): `T+!`, `T*!`, `MATMUL!`, `RELU!`, `SIGMOID!`, `TANH!`, `SOFTMAX!`, `LOG!`, `EXP!`, `TSIN!`, `TCOS!`, `MSE!`, `CROSS-ENTROPY!`, `CONV2D!`, `MAXPOOL2D!`, `BATCHNORM!`, `LAYERNORM!`, `DROPOUT!`.

## 7.2 Обучаемые параметры: `PARAM`

```lisp
(defvar w (param (randn (list 4 2))))   ;; обучаемый вес
(defvar b (param (zeros (list 4))))     ;; обучаемое смещение
```

`param` (примитив `prim_param`) — оборачивает тензор как `requires_grad=true`. Аналог `torch.nn.Parameter(..., requires_grad=True)`.

## 7.3 Forward + Backward

```lisp
;; данные
(defvar x (randn (list 100 4)))
(defvar y (randn (list 100 2)))

;; модель: y = x·w + b
(defun predict (x) (t+! (matmul! x w) b))

;; forward
(let ((pred (predict x)))
  (let ((loss (mse! pred y)))     ;; MSE-loss с записью на ленту
    (grad! loss)                  ;; backward: всю цепочку — в градиенты
    (print (tensor-shape (grad-of w))))))
```

- `(grad! loss)` (примитив `prim_grad_backward`) ≈ `loss.backward()` — проход по ленте в обратном порядке (reverse-topo через `result → producer` карту в `GradientTape`), вычисление градиентов всех `PARAM`-тензоров, очистка ленты.
- `(grad-of w)` (примитив `prim_grad_of`) ≈ `w.grad`.

Внутри `GradientTape::backward(loss, arena)` идёт по dataflow-графу в reverse-topo порядке (потребители раньше производителей), накапливая `+=` градиенты во `inputs`. `GradNode::inputs` хранит `Tensor*` (не SExpr) — autograd не завязан на интерпретатор (см. `src/tensor/CODE.md`).

## 7.4 Оптимизаторы

```lisp
(sgd-step w 0.01)          ;; w -= lr * grad        (SGD) — примитив SGD-STEP
(adam-step w 0.001)        ;; Adam с состоянием m/v на тензоре — примитив ADAM-STEP
```

> 🐍 `(sgd-step w lr)` ≈ `optimizer.step()` для одного параметра. Состояние Adam (`m`, `v`, счётчик шага) хранится прямо на тензоре-параметре (`Tensor::m`, `Tensor::v`, `Tensor::step`).

> ⚠️ **Шаг оптимизатора — это и есть «прочтение» градиента.** `SGD-STEP` и `ADAM-STEP` снимают параметр с учёта `grad_pending_`, то есть засчитывают градиент прочитанным. Читать градиент через `GRAD-OF` не обязательно: достаточно применить шаг оптимизатора.

> ⚠️ **Шаги оптимизатора детектируют нечисловые значения.** `SGD-STEP` и `ADAM-STEP` проверяют веса прямо в цикле обновления и не дают им молча уйти в `inf`: если после шага в весах появились NaN или Inf, оптимизатор поднимает внятную ошибку с именем оптимизатора. Так «тихий inf» в весах становится видимым сразу, а не через эпохи.

Шаг обучения целиком:

```lisp
(defun train-step ()
  (let ((pred (predict x)))
    (let ((loss (mse! pred y)))
      (grad! loss)
      (sgd-step w 0.01)
      (sgd-step b 0.01)
      loss)))          ;; auto-clone: loss переживёт выход из let (гл. 5)
```

## 7.5 Поддерживаемые autograd-операции

| Категория | Операции |
|---|---|
| Арифметика | `T+!`, `T*!`, `MATMUL!` |
| Активации | `RELU!`, `SOFTMAX!`, `SIGMOID!`, `TANH!`, `EXP!`, `LOG!` |
| Loss | `MSE!`, `CROSS-ENTROPY!` (таргеты — целочисленные индексы `[batch]`; backward протаскивает upstream-градиент, так что любой множитель — например reward, — больше не теряется) |
| CNN/нормализация | `CONV2D!`, `MAXPOOL2D!`, `DROPOUT!`, `BATCHNORM!`, `LAYERNORM!` |
| Тригонометрия | `TSIN!`, `TCOS!` |
| FMA (без ленты, чистые SIMD-кирнелы) | `T-FMA`, `T-FMA-RELU` |

Градиент конкретного узла: `(GRAD-OF tensor)` (примитив `prim_grad_of`).

Ядро поддерживает и поэлементные autograd-узлы для экспоненты, логарифма и тригонометрии: `EXP!`, `LOG!`, `TSIN!`, `TCOS!`.

Градиенты в половинной точности (`F16`) работают на уровне тензорного слоя: операции и `GRAD!` не требуют промоушена, gradient seed инициализируется в dtype тензора. **HLO-путь** компилируется только для F32 и I32 (гл. 10).

## 7.6 Сравнение с PyTorch

| PyTorch | Qualisp |
|---|---|
| `w = torch.randn(4, 2, requires_grad=True)` | `(defvar w (param (randn (list 4 2))))` |
| `pred = x @ w` | `(defvar pred (matmul! x w))` |
| `loss = F.mse_loss(pred, y)` | `(defvar loss (mse! pred y))` |
| `loss.backward()` | `(grad! loss)` |
| `w.grad` | `(grad-of w)` |
| `opt.step()` | `(sgd-step w lr)` |
| `opt = Adam(..., lr=0.001); opt.step()` | `(adam-step w 0.001)` |
| `with torch.no_grad():` | обычные операции без `!` (`matmul`, `t+`, …) |

Backward-замыкания (relu, sigmoid, tanh, log, dropout, MSE) и шаги SGD/ADAM работают на сырых F32-указателях; транспонирования исполняются внутри GEMM (флаги `atrans`/`btrans` в `cblas_sgemm`); градиенты не считаются для входов, которые их не запрашивали. Замеры: ag-matmul-1024 — 31 мс, train-sgd/adam-mlp-64 — 1.14 мс; `MSE!` — один fused-проход с double-аккумулятором, без промежуточных тензоров.

## 7.7 Полный пример: линейная регрессия

```lisp
;; y = 2x + 1
(defvar x-data (randn (list 100 1)))
(defvar y-data (t+ (t* x-data (tensor ((2.0)))) (tensor ((1.0)))))

(defvar w (param (randn (list 1 1))))
(defvar b (param (zeros (list 1 1))))

(defun train (iter max-iter)
  (if (> iter max-iter) nil
    (progn
      (let ((loss (mse! (t+! (matmul! x-data w) b) y-data)))
        (grad! loss)
        (sgd-step w 0.02)
        (sgd-step b 0.02)
        (if (equal (mod iter 50) 0) (print loss))
        (train (+ iter 1) max-iter)))))

(train 1 300)
(print w)   ;; ≈ 2.0
(print b)   ;; ≈ 1.0
```

Полный разбор этого и более сложных примеров (MLP, XOR) — в главе 17.

## 7.8 Дифференцируемые функции: `deftape!`

Дифференцируемые функции живут внутри ядра и stdlib (примитивы с вшитой лентой: `net-forward` и соседи). `deftape!` даёт программе описать **свою** дифференцируемую функцию: прямая часть — на Qualisp, обратная — чистая функция, которую лента вызывает сама, дойдя до узла функции.

```lisp
(deftape! square (x) :forward (T*! x x))
(deftape! square (x) :backward (lambda (x y g) (list (t* (t* (tensor ((2.0))) x) g))))
```

**Синтаксис.** `(deftape! NAME (p...) :forward FORM)` регистрирует прямую часть: `FORM` — тело функции, вычисляющее значение по параметрам, и оно же становится привязкой `NAME` в глобальном окружении (как `defun`) — вызов идёт обычным путём. `(deftape! NAME (p...) :backward LAMBDA)` дополняет обратной: `LAMBDA` — лямбда-выражение с параметрами `(p... result adjoint)`, тело которой возвращает **список градиентов по одному на параметр, в порядке параметров**. Сопряжение (`adjoint`) — градиент результата извне: для `x²` производная — `2x·g`, и `g` приходит снаружи. Обе части можно дать одной формой — `(deftape! NAME (p...) :forward FORM :backward LAMBDA)`.

**Контракт операций.** Прямая часть пишется на операциях с `!`, обратная — на обычных тензорных операциях (обратная исполняется во время backward-прохода, и узел, записанный тогда, испортил бы обход). Скалярная арифметика на тензорах не работает в обеих частях: `(* x x)` с тензорным `x` бросает «argument is not a number» — умножение тензоров это `T*`/`T*!`.

**Один узел ленты.** Вызов зарегистрированной функции становится **одним узлом**: прямая часть исполняется с приостановленной записью (её операции не пишут собственные узлы — их обратные стороны добавили бы градиенты к параметрам второй раз), а обратная вызывается лентой при обходе.

**Контракт формы.** Граф ленты живёт в одной форме: ленточная функция не может содержать цикл, а её вызов должен быть в той же форме, где вызван `GRAD!`. Loss — **скаляр**: лента ставит градиенту loss единицу в первом элементе, поэтому векторный loss несёт градиент `(1 0)`.

Проверенный прогон (значение и градиент `x²`; `tests/tape_fn.qlsp`):

```lisp
(deftape! affine (x w) :forward (T*! x w))
(deftape! affine (x w) :backward (lambda (x w y g) (list (t* w g) (t* x g))))

(let ((x (PARAM (tensor ((2.0))))) (w (PARAM (tensor ((3.0))))))
  (let ((v (affine x w)))
    (GRAD! (T*! v (tensor ((1.0)))))   ;; loss — скаляр
    (list (GRAD-OF x) (GRAD-OF w))))   ;; → 3.0 и 2.0
```

> ⚠️ Ошибка **внутри** обратной части (неверный тип операции, неверное число градиентов) прерывает backward и пока завершает процесс неграциозно (крах на выходе из REPL) — проверяйте части на значениях того же типа, что и параметры.

## 7.9 Контракт gradient tape

Лента — не «магический журнал», а объект с правилами владения. Ниже — действующий контракт: что принадлежит ленте, что принадлежит промежуточным значениям и где проходит граница, за которой градиент перестаёт существовать.

### Узлы принадлежат ленте

Нода ленты аллоцируется в куче и удаляется в `tape.clear()`. Буферы ленты не переиспользуются между формами: после `GRAD!` лента пуста, и следующая форма начинает с чистого листа.

### `defvar` промоутит промежуточный тензор

Когда промежуточный результат `MATMUL!` или `T+!` сохраняется через `defvar`/`setq`, его тензор клонируется в stable-scope, а ребро `result` ноды ленты перенаправляется на эту stable-копию. Градиент течёт в тензор, который видит пользователь.

### `reset_scratch` запечатывает незакрытые графы

Если форма верхнего уровня завершилась без `GRAD!`, и какие-то узлы ленты ссылаются на scratch-тензоры, эти тензоры один раз клонируются в stable, и рёбра переписываются. Обучающие циклы ничего не платят — лента пуст после каждого `GRAD!`.

### Adam-состояние живёт на параметре

`m`/`v`/`step` аллоцируются в stable-scope при первом `adam-step` и не умирают с итерацией. Состояние оптимизатора — часть параметра, а не временная величина шага.

### HLO/NS-прокси — строковые хендли

Прокси трассировки — строки `"#hlo-node:<id>"`: id живёт в содержимом строки, поэтому биндинг-копии и promote-клоны сохраняют идентичность. Девять мест создания унифицированы в `Interpreter::make_trace_proxy`, счётчик сбрасывается на `START-TRACE`; `HLO-COMPILE` на чужом хендле бросает внятную ошибку.

### Времена жизни градиентов

Поле `->grad` у нодовых тензоров охраняется деструктор-guard'ами scope: при смерти scratch-региона поле обнуляется, и следующий `backward()` не пишет в переиспользованный пул. Истёкший grad — настоящий null; `GRAD-OF` при отсутствии градиента возвращает свежие нули, а не мусор.

### HLOPROG переживает promote

`clone_to` для HLOPROG-обёртки не возвращает ту же ячейку: `defvar prog (HLO-COMPILE ...)` клонирует обёртку в stable и делит compiled fn (он живёт в кэше компилятора всё время процесса) — после сброса scratch `HLO-RUN` не падает.

### Градиент не переживает границу формы

Это главное правило контракта, и оно легко нарушить нечаянно.

Граф ленты форму переживает (его запечатывает `reset_scratch`), а **градиент — нет**: он аллоцирован в scratch-арене формы, где посчитан `GRAD!`, и умирает вместе с ней. Значение после границы гарантированно нулевое (свежая память, не мусор из переиспользованного пула), а интерпретатор **предупреждает на stderr**: каждый параметр, чей градиент был посчитан, но не прочитан (`GRAD-OF`) и не применён (`SGD-STEP`/`ADAM-STEP`) в той же форме, даёт строку вида:

```text
qualisp warning: grad!: 1 gradient(s) left unread at the form boundary and died with it.
Apply them in the same form as GRAD! (SGD-STEP) or read them there (GRAD-OF) —
training across top-level forms learns nothing.
```

Это предупреждение, не ошибка: намеренно бросить градиент — рабочий паттерн (мёртвый градиент никогда не переиспользуется как scratch — `tests/grad_lifetime.qlsp`). Но программа, которая читает свои градиенты в следующей форме, не сломана — она просто не обучается, и это проходит незамеченным.

Регистрация «прочтения»: `GRAD!` заполняет множество ожидающих параметров, `GRAD-OF`, `SGD-STEP` и `ADAM-STEP` снимают параметр с него; непрочитанные остатки разбираются на границе формы (`flush_form_end`).

### Что это значит на практике

| Сценарий | Поведение |
|---|---|
| `defvar h (matmul! x w)`, а `(grad! loss)` — в **следующей** форме, где `loss` зависит от `h` | Градиент умер на границе формы: значение нулевое + предупреждение. Считать надо в одной форме |
| `defvar pred (matmul! x w)`, `loss = mse! pred y`, `grad!` — в одной форме | Работает: это канонический паттерн |
| `(setq loss (mse! pred y))` (`setq` вместо `defvar`) | Работает; `setq` копирует значение в stable, поэтому промежуточный тензор получает лишнюю копию |
| Adam на 10000 итераций | `m`/`v` живут на параметре, momentum работает корректно |

### `defvar_autograd` (явная конвенция)

Для читаемости — отдельная форма для тензоров-параметров, которые обязаны быть `requires_grad=true` и переживать HibLin-promote:

```lisp
(defvar_autograd w (randn (list 4 2)))
;; эквивалентно (defvar w (param (randn (list 4 2)))),
;; но явно обозначает намерение — параметр автограда.
```

(Реализовано в `stdlib/dl.qlsp` как макрос-обёртка над `defvar` + `param`.)

### Правила для авторов модулей

- Градиенты считаются **только** через `!`-операции: `MATMUL!`, `T+!`, `T*!`, `MSE!`, `RELU!`, `SIGMOID!`, `TANH!`, `SOFTMAX!`, `LOG!`, `EXP!`, `TSIN!`, `TCOS!`, `CONV2D!`, `MAXPOOL2D!`, `BATCHNORM!`, `LAYERNORM!`, `DROPOUT!`, `CROSS-ENTROPY!`. Обратной разницы «обычных» операций нет (`T-!` не существует).
- `GRAD!` = `backward` + `tape.clear()`. После `GRAD!` лента пуста.
- `GRAD-OF` читается в той же форме, где был `GRAD!` — **не просто «стоит», а обязателен**: градиент аллоцирован в scratch-арене той формы, где посчитан, и умирает вместе с ней. Читать его в следующей форме — читать мёртвый буфер, который тихо даёт нули и выглядит как «модель не учится».
- Промежуточные тензоры **не стоит** держать через `defvar` (промоут клонирует тензор — лишняя копия, граф длиннее, чем нужно). Алиасы параметров через `let` остаются в scratch и не платят за копирование.
- Параметры модели объявляются через `defvar` **до** обучения; после — только алиасы через `let`.
- Внутри `while` `GRAD!` делается в каждой итерации (так делает `train-step` из модуля `dl`).

## 7.10 Правило `-ffast-math` и проверка конечности

Release-сборка идёт с `-ffast-math`, а он включает `-ffinite-math-only`: компилятор разрешает предполагать, что NaN и Inf не бывают, и сворачивает `a == b` в `!(a<b) && !(a>b)`, что **для NaN истинно**. На практике это значит:

```lisp
(equal (log -1.0) (log -1.0))   ;; → T   (в release)
```

Отсюда два практических правила:

1. **Конечность проверяется примитивом `(FINITE? t)`.** Это битовая проверка (`Tensor::has_nonfinite`), единственный надёжный способ увидеть NaN или Inf. Ни `equal`, ни сравнение плавающих, ни `std::isfinite` в release с этим не справляются.
2. **Числовые пороги в тестах ставятся выше baseline вырожденного решения.** Если модель может сойтись к «всегда предсказывать самый частый класс», то baseline — доля этого класса, и порог должен быть выше него. Порог ниже baseline проверяет не обучение, а совпадение с вырожденным ответом.

```lisp
;; правильно: конечность — битовым тестом
(assert-eq (FINITE? w) t)

;; неправильно: сравнение плавающих в release не видит NaN
;; (assert-eq (equal (list->tensor weights) (list->tensor saved-weights)) t)
```

## 7.11 Известные ограничения

- HLO fallback-граф (без `HLO-COMPILE`) держит константы формы трассировки — кросс-форменное использование такого HLOPROG небезопасно.
- Shell-линковка HLO-кернела — fallback при сборке без LLD.
- Глубокая не-хвостовая рекурсия переполняет стек; TCO снимает этот предел для self-хвостовых вызовов (гл. 20).
- `TSUM` не пишет градиент (это value-only операция): градиентные суммы собираются через `MATMUL!` с единичным вектором.
