# Глава 20. JIT-компиляция: copy-and-patch

Qualisp компилирует S-выражения в нативный x86-64-код прямо в рантайме — без отдельного компилятора, без LLVM, без байткода и без второго AST. Метод — **copy-and-patch**: эмиттер копирует готовые байтовые стенсилы, патчит адреса хелперов (imm64) и rel32-переходы, после чего страница исполняется. Архитектура — x86-64 SysV с AVX2; компиляция включается сама: top-level форма компилируется и исполняется сразу, тело `defun` компилируется при определении (эмиттер строит `FunctionTemplate` с готовым `entry`). Явных форм `(jit f)` / `(discard-jit f)` в реализации нет — бинарник на них отвечает `unknown function JIT`; управлением кэшем занимается рантайм сам.

> 🐍 **Python-аналогия.** CPython 3.13 JIT — тоже copy-and-patch: стенсилы генерируются LLVM *на этапе сборки* CPython, а в рантайме LLVM нет — интерпретатор байткода копирует готовые машинные блоки и латает дырки. В Qualisp то же самое, но стенсилы выписаны руками и вшиты в бинарник, латает их эмиттер, а единица компиляции — не байткод-хот-цикл, а S-выражение формы. Контраст: Numba компилирует через LLVM IR в рантайме — Qualisp так не делает принципиально.

## 20.1 Идея: нативный код — это кэш

Главный принцип — «инвариант одной формы»: **S-выражение — единственная авторитетная форма программы**. Всё нативное — выбрасываемый кэш, выведенный из S-выражения:

```
Program (root)
  → typecheck
  → Emitter.compile(form) → CodePage
  → CodePage.run() → Value
```

- Эмиттер делает **один проход** по S-дереву, линеаризация LNR: оператор, затем аргументы слева направо; top-level формы — слева направо. Дерево **в момент исполнения не читается**: хелперы видят значения, а не формы.
- Контракт эмиттера: `emit(form, env, expected_type) → Code{bytes, relocations, bail_sites, source_map}`.
- Оригинальное S-выражение остаётся **мастер-формой** внутри `Func`; страница живёт в `StableMemory` и может быть пересобрана из мастера. Функция и её нативная компиляция — один callable-атом: `type-of` и печать едины для лисп-функции и примитива.
- Промежуточного представления нет: никакого байткода, никакого IR, никакого LLVM. Интерпретатора тоже нет — `read → expand → typecheck → emit → run`.

> 🐍 **Python-аналогия.** Как у CPython код-объект — authoritative, а JIT-страница — производный кэш: выбросить её и собрать заново можно в любой момент, семантика от этого не меняется. В Qualisp роль код-объекта играет само S-выражение.

Тот же инвариант решает судьбу нативного в образе: **мастер-формы едут в образе, страницы кода — нет** — они пересобираются из форм (гл. 21). AOT-вставка нативного кода запрещена.

## 20.2 Первый запуск

```lisp
(defun add (a :fixnum b :fixnum) :fixnum (+ a b))
(print (add 2 3))               ;; → 5
```

На `(defun …)` эмиттер компилирует тело: `emitDefun` строит `FunctionTemplate` и через `makeFuncFromTemplate` регистрирует функцию в рантайме. `entry` — уже скомпилированная страница; вызов идёт в неё сразу. Страница — кэш, но создаётся она из мастера, так что результат первого и любого следующего вызова одинаков.

Ручного переключателя нет: `(jit add)` и `(discard-jit add)` в бинарёте — `unknown function`. Внутреннее управление страницами — `JitCache` (§20.5) и `Runtime.adoptPage`; пользователь видит только поведение и диагностику.

### Кэш по узлу формы

`JitCache` (`src/jit/cache.zig`) — хэш-таблица `*Cons → *CodePage`. Ключ — **узел мастер-формы**, а не сигнатура и не env:

- попадание возвращает готовую страницу без повторной эмиссии;
- `clear()` снимает записи кэша, но сами страницы живут до teardown `Runtime`;
- страницы функций принадлежат рантайму (`Runtime.adoptPage`), в кэше лежат top-level страницы.

```lisp
(defun sq (x :fixnum) :fixnum (* x x))
(print (sq 7))                  ;; → 49
```

## 20.3 Что компилируется

Эмиттер (`src/jit/emitter.zig`) покрывает ядро языка:

- литералы `nil`/`t`/fixnum/flonum/char и символьные константы;
- `progn`, `if`, `let`, `setq`, `while`;
- `+ - * / mod`, сравнения `= < <= > >=`, `null`/`not`;
- локальные переменные (слоты кадра), `defun`/рекурсия, `defvar`/глобалы, `lambda`-замыкания (снимок слотов в `env`);
- `cons/car/cdr/list/length`, `print`;
- `&optional`/`&rest`, `and`/`or`/`cond`;
- строки: литералы, `strcat`, `string=`, `string-length`;
- `setq` захваченного биндинга (мутация env-снимка);
- `defstruct`/конструктор/`slot-value`/`set-slot`/`type-of`, `impl` и методы (таблица `tag → func`, диспетч по первому аргументу);
- `throw`/`catch-error` и `(:result T)` (`Result { ok, value }`): `result-ok?`, `result-value`, `result-message`;
- `quote` compound-форм (constant pool), `gensym`, `defmacro`, expander, quasiquote (`,`, `,@`, вложенные уровни), `try`-макрос;
- `the` как проверяемый каст, `atom?`/`list?`, `macroexpand-1`/`macroexpand`, `eval` (проверяемый каст через постоянный checker в `Runtime`).

Всё остальное идёт через хелпер с абсолютным адресом из таблицы; рекурсия и взаимная рекурсия работают — jit-код вызывает jit-код. Ошибка эмиттера — `error.Unsupported`/`BadForm`/`UnknownVariable`, причина в `diag`; компиляция — ускорение, но никогда не условие корректности.

### ABI нативной страницы

Страница — обычная C-функция в SysV x86-64:

```c
void entry(frame: *Value, env: ?*Env, rt: *Runtime, out: *Value);
```

- `rbx` — слоты кадра, `r12` — env замыкания, `r13` — `*Runtime` (инлайн-код читает глобалы без TLS), `r14` — `out` (указатель, куда кал пишет результат). Все четыре — callee-saved.
- Пролог: четыре `push` + `sub rsp, 8` (выравнивание). Эпилог восстанавливает регистры и делает `ret`.
- **Кал сам пишет результат в `*out`** (24 байта `Value`). `out` указывает в кадр вызывающего вызывающего и переживает освобождение кадра — это снимает главный блокер TCO (§20.9).
- Слоты адресуются индексами; размер `Value` знает только Zig-хелпер. Смещения `Runtime`/`Globals` считаются через `@offsetOf` в эмиттере: переезд поля ломает сборку, а не семантику.

**SysV/Win64.** Все JIT-точки (хелперы, `entry`, ядра HLO) объявляются через `jit_abi.call` из `src/jit/abi.zig`: на Linux это `.c` (= SysV), на Windows — явный `.x86_64_sysv`. Zig порождает SysV-функции внутри PE, поэтому байты JIT-страниц **идентичны на обеих ОС**; Win64-соглашение с его shadow space в JIT-коде не используется. Отличаются только системные вызовы W^X.

### Varargs: `&optional` и `&rest`

Маркеры параметров компилируются. `FunctionTemplate` хранит `required`/`optional`/`has_rest`; пролог и `placeArgs` обеспечивают ту же семантику, что и вызовы через `callFunc`: непереданные `&optional` получают `nil`, `&rest` собирается в список хвоста (пустой хвост — `nil`), арность проверяется. TCO-оптимизация для самовызова требует **точной арности и отсутствия** `&optional`/`&rest` (§20.9); остальное идёт обычным вызовом.

### Инлайн fixnum-арифметика

Арифметика и сравнения над fixnum эмитируются несколькими инструкциями: guard тега, `add`/`imul`/`addsd` и **bail-блок на прежний хелпер** (`ql_add`, `ql_lt`, …). Хелпер остаётся единственным владельцем инварианта (в том числе точной int64-семантики с wrap) и вызывается на промахе guard'а. В эмиттере есть тест раскладки `Value` — он фиксирует смещения полей, от которых зависит сгенерированный код. Замер этапа P9e: операция 8.2 → 2.2 нс, `fib` ×1.6.

Здесь **нет интерпретатора как fallback**: guard уводит в хелпер, а не в tree-walk; deopt не реализован — страницы не специализированы, helper-путь и есть generic-путь.

### SIMD и быстрые пути тензорных ядер

Тензорные операции вызываются из JIT-кода как хелперы/ядра, но сами ядра векторизованы через `@Vector`:

| путь | устройство | замер |
|---|---|---|
| `elementwise` / `map` | `@Vector`, 8×f32 / 4×f64; `createUninit` для результатов, перезаписываемых целиком | 524k элементов, `(* p 2.0)`: 28 → 11 мс (~1 нс/элемент, упор в память) |
| `matmul` | обход `i-k-j`, `@Vector` (8 f32 / 4 f64) | 128³: 237 → 17 мс |
| `tsum` / `tmean` | 8 f64-полос, фиксированный порядок сведения | 200×131k: 23 → 7 мс (1.4× от Rust `-O3`) |
| роутер `ns-if` | таблица «ячейка → ветка», типизированные проходы | graph 154 → 59 мс |

Порядок сведения в редукциях зафиксирован: результат детерминирован, но не совпадает с «слева направо». В графах ветки `ns-if` считают куски по `B/4` строк, поэтому бенчмарк-набор от SIMD почти не двигается.

### Прямые глобалы

`Globals` (`src/runtime.zig`) — плотный массив по `SymbolId`: `values: []Value` и отдельный `present: []bool`. JIT читает оба массива напрямую; инвариант — `values[id]` читается только при `present[id] == true`. Отдельный байт присутствия нужен потому, что флаг в `?Value` попал бы в padding, от которого эмиттер не должен зависеть. Быстрый путь чтения — `id < present.len`, байт присутствия, копия 24 байт; отсутствие/рост таблицы уходят в хелпер. Запись инлайнится только для immediate-тегов (`tag <= :symbol`), не-worker и существующего id; heap-значения и рост идут в `ql_set_global` (там `defineGlobal` делает world-копию).

## 20.4 Типы на границе: хелперы и специализация

Специализации по наблюдаемым типам в текущей реализации нет: страница не несёт версию сигнатуры, `JIT-SIG`/`JIT-STALE-P` как форм нет (проверено бинарём), «молодого окна» и пересборки по дрейфу типов нет. Типы проверены чекером до эмиссии; эмиттер не специализирован, поэтому **все нетривиальные операции идут через хелперы**, которые и владеют инвариантом:

- `ql_guard_atom/syntax/int/float/char/symbol/string/bool/nil` — guard'ы на входе;
- `ql_add/sub/mul/div/mod`, `ql_lt/le/gt/ge/eq`, `ql_null` и т.д. — арифметика, сравнения, списки, строки, структуры, результат;
- `ql_load_global`/`ql_set_global`, `ql_call_global`/`ql_call_value`, `ql_tail_prepare`, `ql_make_closure`, `ql_load_env`/`ql_store_env`, `ql_loop_mark/restore/promote`, `ql_macroexpand`/`ql_eval`, `ql_throw`/`ql_catch`.

Инлайн-пути (§20.3) — лишь короткие операции, где хелпер не нужен: литералы, копия слота (16 + 8 байт), чтение immediate-глобала, promotion в `while`, откат итерации. Всё, что сложнее, остаётся в хелпере — это и есть generic-путь.

### Вызовы и хелперы

Вызов функции-значения, примитива, метода по тегу получателя и динамический вызов идут через `ql_call_global`/`ql_call_value`. Хвостовой вызов другой функции использует отдельный `ql_tail_prepare` (§20.9); на промахе он тоже фолбэкает на `ql_call_global` с прежней диагностикой.

## 20.5 Владение страницами: время жизни

`CodePage` — W^X-страница в `StableMemory`: POSIX `mmap`/`mprotect`, Windows `VirtualAlloc`/`VirtualProtect`. Содержимое страницы от ОС не зависит; write-then-execute, никогда не оба режима одновременно.

- `JitCache` ключуется по узлу формы; `clear()` снимает записи, но страницы живут до teardown `Runtime`.
- Страницы функций принадлежат рантайму через `Runtime.adoptPage`; `Runtime` держит список `templates` и страницы до `deinit`. Per-call освобождения нет.
- Struct-инстансы и `Result` тоже живут до `Runtime.deinit`.
- Эпох, инвалидации по `defmacro` и рефкаунта обёрток нет: страница не «стареет», она либо есть в кэше, либо пересобирается из мастер-формы.

### Жизнь страницы: владение рантаймом

Владелец страницы — `Runtime`, а не обёртка. `deinit` проходит по `templates` и страницам и освобождает их; `JitCache.clear()` снимает только записи кэша. Клон функции делит готовый `entry` того же шаблона; отдельной претензии на страницу нет, поэтому «смерть обёртки» не является семантическим событием.

> 🐍 **Python-аналогия.** Как код-объект CPython живёт, пока на него есть ссылка, и умирает вместе с интерпретатором, так и страница Qualisp живёт до teardown рантайма — но в отличие от CPython её можно выбросить и пересобрать из формы без изменения поведения.

## 20.6 Интроспекция и диагностика

Языковых форм учёта JIT нет: `(jit-stats)`, `(mem-report)`, `(prof)`, `(version)` в бинарнике дают `unknown function` (проверено REPL-пробой). Наблюдать поведение можно только через trace (§20.10) и сообщения об ошибках.

| Механизм | Что даёт |
|---|---|
| `qualisp --trace file.json script.qlsp` | Chrome Trace JSON с границами вызовов, HLO-графа и фазы `ns-if` |
| `qprof file.json [--top N]` | таблица `name / calls / total_us / self_us / self%` |
| source map `CodePage.map` | `file:line:col` в сообщении об ошибке рантайма |
| `JitCache.clear()` / `Runtime.deinit` | внутреннее управление страницами, не форма языка |

### Что недоступно из языка

Проверка в REPL фиксирует: `mem-report`, `jit-stats`, `prof`, `version`, `help`, `environment` — `unknown function`. Счётчиков `compiles`/`cache-hits`/`refusals` как алисты нет; точный учёт заменяет trace. Компиляция — не условие корректности: функция без страницы ведёт себя так же, как с ней.

### Source map: `file:line:col`

`CodePage` несёт `map: []MapEntry{start,end,span}` и имя файла. `Emitter.emitExpr` на каждую cons-форму записывает `[start, end) → span`; вложенные формы дают вложенные записи, `lookup` берёт самую внутреннюю. Карта строится при эмите, на исполнение не влияет, стоит ~24 байта на форму и не хранит значений слотов.

Хелпер берёт `@returnAddress()` и зовёт `bailAt(addr, msg)`. Адрес возврата указывает **после** `call`, поэтому lookup идёт по `offset-1`; хелпер, вызванный из другого хелпера, получает адрес сайта вызова параметром. `Error.message` не меняется (его видит `catch-error`), позиция кладётся в `error_location`, CLI печатает `file:line:col: message`:

```text
$ cat err.qlsp
(defun foo (x :flonum) :flonum
  (/ 1.0 x))
(print (foo 0.0))
$ qualisp err.qlsp
nil
err.qlsp:2:3: division by zero
error: RuntimeError
```

`error_message`/`error_location` живут до `clearRunState` (следующая top-level форма) или `deinit`. Инспекция переменных в точке останова — отдельный слой; отладчика с точками останова в текущей реализации нет.

## 20.7 Guard'ы и ошибки

Промах guard'а ставит `RuntimeError` через `Runtime.bailAt` — единственный путь ошибки с позицией. Деоптимизации нет: helper-путь и есть generic-путь, страницы не специализированы, поэтому «шторма bail» и пересборки по сигнатуре не бывает. Ошибки не разматываются через нативный C-стек — только через JIT-кадры; `catch-error` ловит ошибку и чистит `Runtime.error_message`. Исключения не должны пересекать нативный кадр.

## 20.8 Граница статики: `eval`

Единственная документированная граница статики — `eval`: `:syntax → :a`, где `:a` выводится из контекста. Форма заново проходит `expand → typecheck → emit`; несовпадение типа — runtime-ошибка. `eval` возвращает `:syntax`/`:atom` консервативно, конкретика — через `the`. Внутри хвостовой цепочки `eval` запускает вложенную страницу; `enterTailScope`/`leaveTailScope` не дают ей освободить чужой кадр (§20.9).

## 20.9 Хвостовые вызовы: полный TCO

### Calling convention

```
entry(frame: *Value, env: ?*Env, rt: *Runtime, out: *Value) void
```

Кал сам пишет результат в `out` (r14) и делает `ret`. `out` указывает в кадр вызывающего вызывающего и остаётся валидным, пока кал работает, — значит хвостовой вызов может быть **прыжком**, а не вызовом: результат дойдёт до того, кто ждёт его наверху.

Регистры страницы (callee-saved): `rbx` — слоты, `r12` — env, `r13` — `*Runtime`, `r14` — `out`. Пролог: четыре push + `sub rsp, 8`; эпилог восстанавливает их.

### Самовызов: прыжок

`tail_self` не зовёт хелпер. Эмиттер ставит `tail_head` сразу после пролога (параметры уже в своих слотах). Аргументы хвостового вызова сначала вычисляются в **временные слоты**, затем копируются в слоты параметров — поэтому `(f b a)` безопасен — и следует `jmp tail_head`. Кадр, traceback и `out` сохраняются, память кадра не растёт. Условие: тот же кал по имени, точная арность, без `&optional`/`&rest`. Тест на структуру кода проверяет, что хвостовая страница не зовёт `ql_call_global`.

```lisp
(defun tc-sum (n :fixnum acc :fixnum) :fixnum
  (if (= n 0) acc (tc-sum (- n 1) (+ acc n))))
(print (tc-sum 1000000 0))      ;; → 500000500000 — миллион хвостовых вызовов
```

### Другой вызов: `ql_tail_prepare`

Хвостовой вызов другой функции (`emitTailPrepare`) компилируется в вызов

```
ql_tail_prepare(frame, name, first, argc, capacity) → ?*TailTarget
```

- **Кал разрешается в рантайме**: тело `Func` другого участника взаимной пары при эмиссии ещё не существует (ссылка вперёд), поэтому статический адрес недоступен. Разрешение — глобал по имени или метод по тегу получателя.
- `placeArgs` — тот же перенос аргументов, что в `callFunc`: `nil` для непереданных `&optional`, сборка `&rest`.
- Верхняя запись traceback **переименовывается** в имя кала: вызывающий исчез и не должен попадать в ошибку.
- При успехе код грузит `frame/env/entry` из `TailTarget`, кладёт `out` в `rcx`, снимает свой пролог и делает `jmp entry`. Ёмкость кадра передаётся `mov r8d, imm32`, который патчится после эмиссии тела (`tail_capacity_patches`) — регистр не тратится.
- Если кал помещается в текущий кадр, новый кадр не берётся. Иначе — кадр из арены, старый возвращается; владелец цепочки — точка входа (`callFunc`/`callFunction`/`runNested`), она освобождает остаток через `Runtime.tail_frame` после возврата всей цепочки.
- Промах (неизвестное имя, несовпадение арности) — обычный `ql_call_global` с прежней диагностикой.

Предпроход чекера публикует сигнатуры top-level `defun` до проверки программы, поэтому `even-p`/`odd-p` типизируются; вызов до определения — runtime-ошибка.

```lisp
(defun even-p (n :fixnum) :bool (if (= n 0) t (odd-p (- n 1))))
(defun odd-p  (n :fixnum) :bool (if (= n 0) nil (even-p (- n 1))))
(print (even-p 1000000))        ;; → T — миллион взаимных хвостовых вызовов
```

Проверено бинарём: `even-p 1000000` → `t`. В тестах — 1M взаимных вызовов в постоянном числе кадров (`frames.capacity < 64`), переполнение/`&optional`/`&rest`, `eval` внутри взятого кадра, переименование traceback, `catch-error`.

### Bump-арена кадров

Кадры вызова живут в `Runtime.frame_area` — неподвижный слот с указателем `frame_top`. `takeFrame`/`giveFrame` — указатель вверх/вниз, освобождение — вычитание размера, порядок строго LIFO (в Debug сверяется указатель). `replaceFrame` заменяет кадр на месте для хвостового вызова с большим калом. Ёмкость фиксирована (~1M слотов по коду в `src/runtime.zig`); исчерпание — типизированная ошибка `call depth limit exceeded` **с позицией**, а не OOM и не segfault. Машинный стек поднят до 256 МБ, чтобы арена успела сработать раньше переполнения стека.

Почему не регистровые аргументы (этап D): фиксированная цена вызова ~10.6 нс против 1.3–1.5 нс на аргумент; кал всё равно спиливает значение в слот. Прямой мономорфный вызов (P9l) выигрыша тоже не дал — 9 нс на вызов — это не диспетчер, а пролог/эпилог страницы, копирование 24-байтных `Value` и косвенный `call`. Вместо этого — дешёвая арена кадров.

### Регион петли и откат итерации

`while` использует `Runtime.loop_marks`: store mark + scratch mark; внешние `setq` копируются в world через `ql_promote`. Откат итерации (`ql_loop_rewind`) **не эмитится**, если условие и тело не могут трогать scratch: анализ консервативный (`Emitter.mayAllocate`) — литералы, арифметика, сравнения, `if`/`let`/`while`/`progn`/`and`/`or`, чистые примитивы (`car`, `nth`, `tref`, `length`) не аллоцируют, а вызовы, `cons`/`list`, строки, тензоры, `lambda`, `defvar`, `setq` глобала — аллоцируют. Решение проверяется и по коду, и по поведению. Ошибка анализа стоит памяти или скорости, но не семантики: rewind только освобождает память.

## 20.10 Отладка и профилирование

Профайлер — **инструмент, не фича языка**: форм `profile-start`/`profile-stop` нет, включается только снаружи:

```
qualisp --trace trace.json script.qlsp
qprof trace.json --top 10
```

Пишется Chrome Trace JSON: события `B`/`E`, микросекунды, `pid=1,tid=1`. Трасса пишется и при ошибке (`defer` в `main`). Инструментированы только точки, невидимые из AST: границы вызовов функций, вызов HLO-графа, фаза `ns-if`. Когда трасса не запрошена, каждый хук — одна проверка `active`. Компиляция JIT-страницы входит в inclusive-время первого вызова: отдельного события «компиляция» нет, поэтому первый вызов всегда дороже.

Агрегатор `tools/qprof` (на Rust; в снапшоте — готовый бинарник) печатает число вызовов и self/inclusive время. Проверено бинарём:

```text
$ qualisp --trace fib.json fib.qlsp
6765
$ qprof fib.json --top 5
trace: fib.json (43782 events)
name                          calls       total_us        self_us   self%
FIB                           21891      726467.0        53923.0  100.0%

total self time: 53923.0 us
```

`qprof` без аргументов → `usage: qprof <trace.json> [--top N]` (exit 2); `qprof --help` трактует флаг как имя файла.

Отладчика нет: source map даёт позицию, но не инспекцию слотов и не точки останова (это отдельный слой). Нет и дампа страниц по переменной окружения — hexdump со стенсилами можно снять только внешним дизассемблером по адресу страницы.

## 20.11 Ограничения и что дальше

- Стенсилы и ABI хардкодят **x86-64 SysV**; других архитектур и бэкендов нет. На Windows байты страницы те же, отличаются только `VirtualAlloc`/`VirtualProtect`.
- Deopt не реализован: страницы не специализированы, guard ставит `RuntimeError`, generic-путь — хелперы. Deopt появится вместе со специализацией.
- Нет регистрового аллокатора: значения идут через слоты памяти (16 + 8 байт на `Value`).
- Struct-инстансы и `Result` живут до `Runtime.deinit`; per-call освобождения нет.
- Ошибки не разматываются через нативный C-стек, только через JIT-кадры; исключение не должно пересекать нативный кадр (у страниц нет `.pdata`).
- Языковых форм `(jit f)`, `(discard-jit f)`, `(jit-stats)` нет — страницами управляет рантайм; наблюдений и JIT-сигнатур в образе нет (гл. 21).
- `JitCache.clear()` снимает кэш, но страницы живут до teardown; `load-image` пересобирает JIT из мастер-форм (гл. 21).
- Замеры ReleaseFast (`CHANGELOG.md`): fib 42 мс, matmul 16 мс, reduce 6 мс, ns-if graph 58 мс (эталон — Rust `-O3`). Относительные улучшения по этапам P9: fib(30) −11 %, loop-id −9 %, взаимная рекурсия с разными кадрами −8 %, вызов ~1 нс дороже после учёта кадра; 1M хвостовых вызовов в постоянном числе кадров.

Тесты: `src/jit_test.zig` (170 тестов) — эмиттер, ABI, source map, кэш, TCO и бэктрейсы; `src/runtime_test.zig` — арена кадров, непересечение/переиспользование, типизированное исчерпание; `src/profile_test.zig` — трассировка; бенчмарки — `bench/fib.qlsp`, `bench/matmul.qlsp`, `bench/reduce.qlsp`, `bench/nsif_*.qlsp`.
