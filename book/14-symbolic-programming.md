# Глава 14. Символьное и нейросимвольное программирование

Qualisp — не просто «Лисп для тензоров»: в ядро встроен **символьный движок** и поверх — **нейросимвольный маршрутизатор** (`NS-IF`/`NS-GRAD!` с guilt detector). Это делает Qualisp подходящим для expert systems, knowledge graphs и нейросимвольного AI.

Реализация — `src/symbolic/engine.cpp` (специальные формы символьного слоя), `src/ns/route.cpp` (нейросимвольный роутер) и встроенные примитивы (`MATCH`, `UNIFY`, `SUBST`, `DEFRULE`, `ASSERT-FACT`, `RUN-RULES`, `QUERY`, `AMB-LET`, `REQUIRE`, `AMB-COLLECT`, `DEFINE-COMPILER-MACRO`, `DEFHLOOP`, `NS-IF`, `NS-GRAD!`).

## 14.1 Pattern matching: `match`

Специальная форма `MATCH` → `Interpreter::do_match`:

```lisp
(match value
  (pattern-1 результат-1)
  (pattern-2 результат-2)
  (_ дефолт))
```

Паттерны (см. `match_pattern` в `engine.cpp`):

| Паттерн | Что сопоставляет |
|---|---|
| `_` | что угодно (wildcard) |
| `?x` или `(? x)` | что угодно, связывает переменную `x` |
| `42`, `3.14`, `"hi"`, `nil`, `'sym` | литерал |
| `(quote val)` | литерал (явно через `quote`) |
| `(list a b)` | список фиксированной длины |
| `(cons h t)` | cons-ячейка: голова + хвост |
| `(or p1 p2)` | любой из паттернов |
| `(when p guard)` | паттерн + предикат-guard |
| `(quote x)` | литерал |

Примеры:

```lisp
(match 42
  (42 "сорок два")
  (_ "другое"))                       ;; → "сорок два"

(match (list 1 2 3)
  ((list ?a ?b ?c) (+ ?a ?b ?c))
  (_ 0))                              ;; → 6

(match (cons 1 2)
  ((cons ?a ?b) (+ ?a ?b)))           ;; → 3

(match (list 1 2 3)
  ((list ?x ?y ?z) (when (> ?x 0)) (+ ?y ?z))
  (_ 0))                              ;; → 5
```

> 🐍 **Python-аналогия.** Это `match/case` из Python 3.10+, но с настоящими биндингами переменных по структуре:
> ```python
> match value:
>     case [a, b, c]: return a + b + c
>     case _: return 0
> ```

Если ни один паттерн не подошёл — `match` бросает `runtime_error` (`throw std::runtime_error("match: no pattern matched")`).

## 14.2 Унификация: `unify` и `subst`

Унификация — сердце Prolog: найти подстановку переменных, при которой два выражения совпадут (с проверкой occurs check):

```lisp
(unify '(?x) '(foo bar))             ;; → ((?X . (FOO BAR)))
(unify '(f (?x) b) '(f a b))         ;; → ((?X . A))
(subst '((?x) . replacement) expression)   ;; применить подстановку
```

Логические переменные — символы, начинающиеся с `?` (`is_lvar` в `engine.cpp:79`): `?x`, или cons-форма `(? x)`.

Реализация (`engine.cpp:78-112`): структурная унификация через `walk`/`occurs`/`extend`/`unify_terms`. `occurs` предотвращает бесконечные циклы (X = f(X) недопустимо).

> 🐍 В Python унификацию делают библиотеки типа `unification`/`kanren` — в Qualisp она встроена.

## 14.3 Property lists: свойства символов

Каждый символ может нести словарь свойств (глобально, в stable-памяти). Реализация — `register_plist_primitives` (`engine.cpp:116-145`): `plist_map` — `unordered_map<Symbol*, unordered_map<Symbol*, SExpr*>>`. При `PUT` значение клонируется в `stable_scope()`.

```lisp
(put 'cat 'legs 4)
(get 'cat 'legs)        ;; → 4
(symbol-plist 'cat)     ;; все свойства
(remprop 'cat 'legs)
```

Оптимизация: для `fixnum`/`flonum`/`symbol`-значений PUT **обновляет in-place** (без нового конс-ячейки).

Жизненный цикл значения в plist такой же, как у любой структурной ячейки: `PUT` по существующему ключу переписывает значение (старое освобождается по общему RC-контракту, гл. 5.5), `REMPROP` убирает свойство досрочно. Таблица свойств переносится в образ мира при `LOAD-IMAGE` (гл. 21).

> 🐍 Это «атрибуты у enum'ов»: `class Animal(Enum): CAT = ...` + `CAT.legs = 4`. Классика Common Lisp, удобна для метаданных.

## 14.4 Rule engine: факты и правила

Forward-chaining движок. Факты хранятся в `kb_facts` (`vector<SExpr*>`, элементы `clone_to(root_arena_)` для immortality). Правила — в `rules_db` (`vector<Rule>`), где `Rule { name, whens, asserts }`.

```lisp
;; факты (цитируются — это данные)
(assert-fact (warm-blooded? cat))
(assert-fact (has-fur? cat))
(assert-fact (live-birth? cat))

;; правило: все тёплые+шерсть+живорождение — млекопитающие
;; Синтаксис 1: (WHEN ...) (ASSERT ...) clauses
(defrule mammal ((? x))
  (when (warm-blooded? (? x))
        (has-fur? (? x))
        (live-birth? (? x)))
  (assert (mammal? (? x))))

;; Синтаксис 2: через =>
(defrule mammal2 ((? x))
  (warm-blooded? (? x))
  (has-fur? (? x))
  =>
  (mammal? (? x)))

(run-rules)                    ;; прогнать вывод (до 100 итераций по умолчанию)

(query (mammal? cat))          ;; → подстановки (здесь (((?X . CAT))))
(query (mammal? (? who)))      ;; → все решения переменной who
(retract-fact (has-fur? cat))  ;; убрать факт
```

Реализация (`do_defrule`/`do_run_rules`/`do_query`):

- Каждое правило парсится: `(when cond1 cond2 ...)` → `whens`; `(assert fact1 fact2 ...)` или после `=>` — `asserts`. Оба списка клонируются в root (immortal).
- `find_bindings(whens)` перебирает все факты в KB, унифицирует whens-цепочку с фактами, собирает все успешные подстановки.
- `run-rules` итерирует до фиксации (`max=100` итераций) или пока добавляются новые факты.
- `query pattern` унифицирует pattern со всеми фактами, возвращает список подстановок.

Правила могут **цепляться** (выведенный факт запускает следующие правила).

### Корректность rule engine

Движок держит три инварианта, на которые опирается остальная символьная часть:

- **Производные факты переживают границу формы.** `do_run_rules` кладёт в KB копии ячеек в корневой области, а не сырые scratch-ячейки: при `reset_scratch` cons-ячейки возвращаются в пул, и `query` в следующей форме иначе читал бы переиспользованную память.
- **Последовательная унификация цепочки `when`.** Клаузы `when` матчатся не по отдельности, а с протянутой подстановкой: переменная, связанная первым клаузом, видна второму, и в `assert` уходит полное решение, а не только первое совпадение.
- **`do_defrule` не теряет клаузы.** Парсер правила append-only в порядке исходника: правило с двумя `(assert)` сохраняет оба, head-паттерн рядом с `(when)` не теряется. Список переменных правила (head) документируется и в матчинге не участвует.

Регрессии на эти инварианты живут в `tests/symbolic_neuro.qlsp` (chaining, рекурсивный ancestor до фикс-поинта, no-false-positive, multi-assert, head-with-when).

> 🐍 Прямого аналога в Python нет — это territory pyDatalog/CLIPS/Prolog. Но обратите внимание: факты и правила — обычные S-выражения, их можно строить макросами (гл. 12).

## 14.5 Недетерминизм: `amb-let`, `require`, `amb-collect`

Логическое программирование через «amb» (ambiguous choice) с бэктрекингом (через `AmbFail` exception):

```lisp
(amb-collect
  (amb-let ((x 1 2 3) (y 1 2 3))
    (require (> (* x y) 4))
    (list x y)))
;; → ((2 3) (3 2) (3 3)) — все пары (x y), где x*y > 4

(amb-collect (amb-let ((x 1 2 3)) (require (> x 1)) x))
;; → (2 3) — генератор без require перечисляется целиком

(amb-collect (+ 1 2))   ;; → (3) — аргумент без генератора вносит одно решение
```

Реализация (`do_amb_let`/`do_require`/`do_amb_collect`):

- `amb-let` создаёт декартово произведение значений переменных и перебирает индексы (`std::vector<size_t>`), пока `body` не упадёт в `AmbFail`.
- `require` — **ограничение бэктрекинга, а не загрузчик модулей**: условие должно быть `T` или `nil`, любое другое значение — внятная ошибка («REQUIRE is a backtracking constraint, not a module loader»). Условие `nil` (ложь) бросает `AmbFail`, и перебор переходит к следующей комбинации; модули грузятся через `IMPORT`/`LOAD`.
- `amb-collect` перечисляет **все** решения каждого генератора-аргумента: успех под сбором — не ответ, а запись в список, после которого перебор продолжается до исчерпания пространства.
- Аргумент без генератора вносит ровно одно решение: `(amb-collect (+ 1 2))` → `(3)`; вложенный `amb-let` под внешним сбором отдаёт своё перечисление как одно значение — собирает только внешняя форма.

> 🐍 Аналог — `itertools.product` + фильтр: `[(x, y) for x in xs for y in ys if x*y > 4]`.

## 14.8 Нейросимвольный слой: `NS-IF` и `NS-GRAD!`

Уникальная конструкция Qualisp: **нейросимвольное дерево**. Символьная развилка `NS-IF` маршрутизирует данные в одну из нейросетевых ветвей, и автоградиент (гл. 7) корректно распределяет ошибку через `NS-GRAD!`.

Реализация — `src/ns/route.{hpp,cpp}` (классы `RouteHop`, `Router`, `GuiltDetector`, `GuiltVerdict`).

```lisp
(defvar logits (matmul! x router-w))    ;; логиты решения

(defvar pred (ns-if logits
  (("dog") (matmul! x dog-net))         ;; ветка «собака»
  (("cat") (matmul! x cat-net))))       ;; ветка «кошка»

(defvar loss (mse! pred y-true))
(ns-grad! loss 'cat)                    ;; backward с учётом маршрута
```

Специальная форма `NS-IF` → `Interpreter::do_ns_if` (`interpreter.cpp:694`):

1. Принимает логиты `[N]` (один образец) или `[batch, N]` (батч).
2. Каждая ветвь задаётся `(("label1" "label2") body...)` — `branch_covers` описывает, какие ground-truth-метки покрывает ветвь.
3. Выбирает ветвь per-sample по argmax, записывает `RouteHop` в `Router`, возвращает результат **первой выбранной ветви** (для чистого батча корректно; для смешанного — маршрут/guilt верны).
4. Вне трассировки градиент через развилку не течёт автоматически — лента **разорвана на точке выбора** (обучение через `NS-GRAD!` ниже). Под трассировкой `NS-IF` строит **ROUTE-ноду HLO-графа** с per-sample исполнением ветвей — см. гл. 10.7.

`NS-GRAD!` → `do_ns_grad` (`interpreter.cpp:768`):

1. Принимает loss и label (символ/строка или список).
2. Вызывает `GuiltDetector::detect`, который для каждого образца находит **первый (ближайший к корню) хоп**, где `taken != correct` (`RouteHop::resolve_correct`).
3. Если расхождений нет → `GuiltKind::NONE` (виновен лист); иначе `GuiltKind::ROUTING` (виновен маршрутизатор).
4. Per-sample softmax-weighted STE в `decision_logits->grad`. Знаки **канонизированы**: сид соответствует градиенту `−log p(correct)` = `(p − onehot)`.
5. **Блокировка** tape-узлов взятой ветви — строго по виновным хопам (`per_sample_hop`): блокируется только диапазон ленты виновного хопа, поэтому STE-градиент доходит до весов виновного роутера, а корневой узел ленты остаётся разблокированным (регрессия `ns-nested-breed-guilty`).
6. Затем `GradientTape::backward(loss, arena, blocked)` идёт в reverse-topo с пропуском заблокированных.

### Что «виновно»

| Случай | Виновник | Градиент |
|---|---|---|
| Маршрут верный | лист | в листовую ветвь (нормальный backward) |
| Развилка неверна (per sample) | маршрутизатор | per-sample STE в логиты развилки; виновные ветви блокируются |
| Глубокое дерево | первый расходящийся узел | STE туда; подветви блокируются |
| Смешанный батч | по образцу | STE/блокировка per-sample; правильные сохраняют градиент |
| OR-overlap (несколько покрывающих ветвей) | taken-ветвь первая | если она покрывает label → вердикт NONE (виновен лист) |

### Почему это уникально

> 🐍 Это гибрид `nn.Module` с `torch.gather`-маршрутизацией и hard attention: представьте дерево if-ов, где каждая развилка — обучаемая нейросеть, и весь граф дифференцируем. В PyTorch такого из коробки нет — здесь это две формы языка.

## 14.9 SECOND-BEST и NS-RL поверх слотов

> Полный обзор движка blackit (роадмап T1–T4) — в разделе 14.10; здесь — вехи внутри символьного слоя.

### `SECOND-BEST` — откат маршрута

`SECOND-BEST` — индекс второго по величине значения (флэт как `ARGMAX`); связи пика разрешаются на соседнее вхождение (`(1 5 5)` → 2), откат никогда не выбирает тот же маршрут. Полный сценарий — `examples/ns_validate.qlsp`: скорер предлагает argmax, база правил отвергает (нет производного факта `recognizable`), конвейер откатывается на second-best, и `NS-GRAD!` назначает вину роутеру за запрещённый маршрут.

### NS-IF поверх макро-слотов (blackit T4)

Роутер маршрутизирует не по ветвям-замыканиям, а по **макро-слотам** (гл. 12.11):

```lisp
(ns-route logits slots)         ;; argmax → слот
(ns-route-sample logits slots)  ;; softmax-сэмплинг слота
(ns-route-index logits k)       ;; явная ветка (для eps-greedy)
```

Роутер обучается штатным `NS-IF` + `NS-GRAD!` (STE/guilt, знаки канонизированы). Полный агент-кодер: фаза 1 пишет `(lambda (x) (qdbl (qinc x)))` через слот+песочницу (42 эпизода, reward 1.0, проверка f(5)=12), фаза 2 — NS-IF-роутер над слотами 4/4 (`examples/nsrl_coder.qlsp`; абляция slot-path vs чистый REINFORCE — сходятся оба).

## 14.10 Движок blackit: NS-RL

**blackit** — кодовое имя роадмапа нейросимвольного RL (T1–T4). Это движок, в котором символьная система обучает **собственный код** методом усиления: от примитива выборки до агента, который пишет Qualisp-код текстом и маршрутизирует через обученные макро-слоты.

| Стадия | Что даёт | Где живёт |
|---|---|---|
| **T1 — REINFORCE-ядро** | примитив `SAMPLE` (категориальный softmax-сэмплинг one-hot, детерминированный сид), `reinforce-loss!` = reward × `CROSS-ENTROPY!(logits, action-index)` с градиентом `reward·(p − onehot)` | ядро + `stdlib/dl.qlsp`; `tests/nsrl_t1.qlsp` (8 тестов: ручные значения CE, знаки градиентов при ±reward, детерминированный 2-рукий бандит сходится) |
| **T2 — слоты политики + песочница** | макро-слоты (`SLOT-SET` — переобучение заменой формы), `EVAL-SANDBOXED` (бюджеты шагов/глубины/cons; запрет DEF*-форм, файловых/сетевых/sleep-примитивов, setq глобалов), `CATCH-ERROR` как настоящий примитив | ядро; `tests/nsrl_t2.qlsp` (29 тестов: исчерпание бюджетов, отказ опасных форм, переобучение слота, полный цикл агента) |
| **T3 — кодер** | агент собирает Qualisp-код **текстом** из своих DSL-макросов: `dsl-body-text`/`coder-form-text` → `READ-FROM-STRING` → слот → песочница; награда — доля зелёных проверок на парах (input . output) | `stdlib/ns.qlsp`: `task-reward`, `slot-task-reward!`, `ns-train-coder!` (2-шаговый REINFORCE с baseline; сходимость = 5 идеальных эпизодов подряд); `tests/nsrl_t3.qlsp` |
| **T4 — маршрутизация по слотам** | `ns-route` (argmax→слот), `ns-route-sample` (softmax), `ns-route-index` (явная ветка для eps-greedy); роутер обучается штатным `NS-IF` + `NS-GRAD!` (STE/guilt, знаки канонизированы) | ядро + `stdlib/ns.qlsp`; `tests/nsrl_t4.qlsp` (dispatch по argmax, сходимость роутера 4/4, ветка-свап, переобучение слота видно хосту) |

### Полный цикл агента

```text
1. Агент сэмплирует DSL-макросы (SAMPLE) и собирает код ТЕКСТОМ (dsl-body-text)
2. Текст → READ-FROM-STRING → SLOT-SET → EVAL-SANDBOXED (бюджеты)
3. Прогон проверок на парах (input . output) → task-reward (доля зелёных)
4. ns-train-coder! — 2-шаговый REINFORCE с baseline
5. Маршрутизация между обученными слотами — ns-route (T4)
```

Демо `examples/nsrl_coder.qlsp`: фаза 1 — агент пишет `(lambda (x) (qdbl (qinc x)))` через слот+песочницу (42 эпизода, reward 1.0, проверка f(5)=12); фаза 2 — NS-IF-роутер над слотами 4/4. Абляция: slot-path vs чистый REINFORCE сходятся оба (42 vs 46 эпизодов на демо-задаче) — слоты дают структуру, а не только скорость сходимости.

Механика движка — stdlib + четыре примитива ядра (`SAMPLE`, `EVAL-SANDBOXED`, `APPLY`, `CATCH-ERROR`) + слоты: blackit расширяется без изменения компилятора — гомоиконность в деле (гл. 12.11).

## 14.11 Когда символьный слой полезен

- Expert systems поверх ML-моделей: правила фильтруют/маршрутизируют предсказания (`NS-IF` маршрутизирует в ветвь, обученную под конкретный класс; правила могут менять label-set).
- Knowledge representation: факты + унификация + запросы без внешнего Prolog.
- Обучаемые решающие деревья с нейросетями в листьях — `NS-IF` ровно про это.

Символьный слой живёт на S-выражениях в stable-памяти (гомоиконность), нейронный — компилируется через HLO (гл. 10). Qualisp сознательно разделяет эти миры: интроспекция правил не мешает нативной скорости тензоров.

## 14.12 Известные ограничения

- `unify`: нет backtracking (механизм `AMB-LET` компенсирует это, но не сама `unify`).
- `match`: нет type-check паттернов (`(tensor ?x)` не работает — будет интерпретировано как cons-литерал).
- `NS-IF`: для смешанного батча исполняется ветвь первого образца (маршрут/guilt per-sample верны, но forward-вычисление — только по взятому маршруту).
