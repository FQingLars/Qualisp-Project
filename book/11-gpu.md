# Глава 11. Вычисления и платформы

В текущей реализации отдельного типа `Device` и GPU-бэкенда нет. Вычисления
выполняются на CPU x86-64: JIT и скомпилированные HLO-графы вызывают нативные
ядра с SIMD AVX2. Ниже описано, как этот путь устроен и на каких платформах он
работает.

## 11.1 Устройство одно: CPU

Тензор — это dtype, конкретная форма и плоский буфер в памяти хоста. В
перечислении владельцев буфера есть только `scratch`, `world` и `pool`
(гл. 5); `device` там нет. В исходниках нет CUDA-, ROCm-, Vulkan-, Metal- или
OpenCL-кода, а также типов `Device`/`DeviceType` и функций вроде
`device-info`, `device` или `gpu-info` — все они дают `unknown function`.

```text
Tensor = { dtype, shape: []usize, storage: []T, owner: scratch|world|pool }
```

JIT-эмиттер хардкодит x86-64 SysV: пролог, эпилог, хвостовые прыжки и адреса
хелперов — одни и те же на всех поддерживаемых ОС. Других архитектур нет.

## 11.2 Интерфейс ядра вместо Device

Роль «устройства» играют сами ядра — обычные C-ABI-функции на x86-64.
Например, скомпилированный граф вызывает `ql_hlo_add`, `ql_hlo_mul`,
`ql_hlo_matmul` и соседние хелперы; каждый читает указатели тензоров из
`HloFrame`, выделяет результат из `frame.pool` и пишет его в слот выхода.
Ошибка выставляется флагом на кадре, а не ветвлением в сгенерированном коде.

```zig
pub export fn ql_hlo_add(frame: *HloFrame, out: u32, a: u32, b: u32)
    callconv(jit_abi.call) void { ... }
```

`jit_abi.call` — `.c` на Linux (то есть SysV) и `.x86_64_sysv` на Windows: Zig
порождает SysV-функции даже внутри Windows-бинарника, поэтому байты JIT-страниц
идентичны на обеих ОС. Никаких `memcpy_to_device`/`sync`/`launch_*`-методов и
таблицы виртуальных функций нет: вызов ядра — прямой вызов по фиксированному
адресу, сконфигурированный эмиттером.

> 🐍 **Python-аналогия.** Ближе всего `torch.set_default_device('cpu')`: код не
> знает об устройстве и просто работает на CPU. Но в отличие от PyTorch здесь
> нет переключателя бэкенда — сам вопрос о выборе устройства в языке не
> существует.

## 11.3 Интроспекция

Функции `device-info` и ей подобных нет. Узнать, на чём выполняется код, можно
из окружения сборки и CLI:

```text
$ qualisp --version
qualisp 0.19.16
```

Тип значения узнаётся через `type-of` — тензор даёт `TENSOR` (гл. 4). Ни
рантайм-перечисления устройств, ни флага `GPU` в языке нет.

## 11.4 Почему CPU хватает

Горячие пути тензорных операций векторизованы через `@Vector`:

- `elementwise`/`map` — 8×`f32` или 4×`f64` за итерацию; параллельно по
  элементам (порог ~256K);
- `matmul` для 2-D — обход `i-k-j` с `@Vector` (8 f32 / 4 f64); параллельно
  по строкам результата (строки независимы);
- `reshape`/`transpose` — копируют и параллелятся по строкам;
- `tsum`/`tmean` — 8 полос `f64` с фиксированным порядком сведения:
  результат детерминирован, но не «слева направо»; параллельно по partial'ам:
  chunk'и → полосы → хвост, бит-в-бит как serial;
- NS `fillBand`, выбор ветки, `countingSort`, `gatherRows`/`scatterRows` —
  параллельно по chunk'ам; `countingSort` использует гистограммы и курсоры,
  сохраняя stable-порядок строк в бакете; `Uncovered`/`Overlap` детектируются
  после параллельного прохода;
- `defuse` — скалярный f32-цикл x86-64 без промежуточных тензоров, AVX2 по
  8 f32 + scalar-tail;
- Ядра reduce и elementwise работают с `f16`/`f32`/`f64`/`u8`, для `u8` сохранены
  точные операции с округлением/clamp.

Параллельные ветки идут через `src/kernel_pool.zig` — пул вычислительных ядер,
отдельный от пула компиляции HLO. Воркеров `max(1, min(cpu-1, 8))`, создаются
они лениво на первом достаточно большом вызове; у них нет `Runtime`, входные и
выходные буферы выделяет вызывающий, а общие `frame.pool`, `grads[]`, `rt.trace`
и scope-арены остаются на одном потоке. Вложенный параллелизм на воркерах
отключён; маленькие входы остаются последовательными, `QUALISP_SERIAL=1`
отключает пул полностью. Тесты `src/parallel_test.zig` сверяют parallel и serial
**побайтно** (elementwise/map/sum/mean для `f32`/`f64`, matmul 128×128, NS
route+gather на 65536 строках). A/B ReleaseFast, 16 ядер: matmul 15.9 →
**7.6 мс (2.10×)**, ns-if eager 84.9 → 79.0 мс, graph 59.9 → 60.4 мс,
reduce 5.1 → 5.7 мс, fib без изменений. Остаток одной нити в ns-if — сами
branch-лямбды (4 ветки).

> 🐍 **Python-аналогия.** Это уровень ручной векторизации под AVX2: как если бы
> NumPy/PyTorch CPU-путь был заточен под конкретный x86-64 без возможности
> переключиться на CUDA.

## 11.5 Связка с HLO

Графы `defgraph` и fused-тела `defuse` компилируются в машинный код x86-64 на
страницах W^X: `mmap`/`mprotect` на POSIX, `VirtualAlloc`/`VirtualProtect` на
Windows. Содержимое страниц от ОС не зависит (§11.2). Скомпилированный граф
вызывает те же C-ABI ядра, что и eager-путь; backward компилируется в обратную
последовательность вызовов `ql_bwd_*`. Вызов графа ленив, первый вызов ждёт
готовности страницы.

Машинный стек поднят до 256 МБ: на Linux CLI делает `setrlimit`, на Windows тот
же резерв задаётся в PE-заголовке (`stack_size` в `build.zig`). Это нужно, чтобы
глубокая рекурсия сначала получила диагностику арены кадров (гл. 5), а не
segfault.

## 11.6 Практические советы

1. Пишите код без оглядки на «устройство» — его нет, вычисления идут на CPU.
2. Крупные батчи сразу кладите в тензор: путь идёт через SIMD-ядра, а не через
   циклы по спискам.
3. Для elementwise-выражений, которые повторяются в графе, используйте
   `defuse`: он компилируется в один цикл с AVX2.
4. Помните, что `reshape`/`transpose` копируют (гл. 6): это доминирует над
   стоимостью самого ядра на больших тензорах.
5. Параллелизм крупных ядер включается сам; `QUALISP_SERIAL=1` возвращает
   последовательный путь (гл. 6).

## 11.7 Вычислительный стек в коде

```text
   S-выражение (мастер-форма)
              │
     ┌────────┴────────┐
     ▼                 ▼
  JIT copy-and-patch   HLO-граф / defuse
  (страница W^X)       (скомпилированная страница W^X)
     │                 │
     └────────┬────────┘
              ▼
   kernel_pool: parallel-диапазоны (elementwise/map/matmul/
   reshape/transpose/sum/mean, NS router/compaction)
              ▼
   C-ABI ядра (ql_hlo_*, ql_bwd_*, ql_*)
              ▼
   x86-64 SysV + AVX2 (@Vector)
              ▼
   Linux x86-64 / Windows x86-64 (SysV-код внутри PE)
```

Маленькие входы вызывают ядра напрямую, минуя пул. Специализация-lite
(unguarded fixnum-арифметика по типам от чекера) измерена и откатана:
arith-loop 18.15 → 18.26 нс, calls 33.51 → 32.68 нс, fib 42 → 43 мс;
JIT компилирует функцию один раз и мономорфным не является. Реальный выигрыш
дали unboxed fixnum-локальные (M3a: 10.2 → 3.2 нс, 14.9 → 4.5 нс; гл. 5, 20).

## 11.8 Известные ограничения

- **GPU-бэкенда нет.** Ни CUDA, ни ROCm, ни Vulkan/Metal в проекте не
  встречаются; `device-info` и `Device` тоже отсутствуют.
- **Параллелятся только ядра с непересекающимися выходами:** elementwise/map,
  matmul, reshape/transpose, sum/mean и NS router/compaction. `max`, `softmax`,
  `argmax`, `reduceToShape` остаются последовательными (global-редукция или
  read-modify-write выхода); воркеры не имеют `Runtime`, вложенный параллелизм
  на них отключён.
- Поддерживаются только `x86_64-linux-gnu` и `x86_64-windows-gnu`/`-msvc`
  (Windows — с оговорками); других архитектур нет, эмиттер хардкодит x86-64.
- SIMD — AVX2; NEON и «скалярный путь для другой архитектуры» в реализации
  отсутствуют.
- Нет асинхронных операций над устройствами: `memcpy`/`sync`-интерфейса нет.
- FFI-трамплин и файловые хэндлы — платформенные, но JIT-код от этого не
  меняется: на Windows хэндлы — токены поверх `std.Io.File`, FFI вызывает целевую
  C-функцию с нативным Win64 ABI (регистры по позиции аргумента, 32 байта
  shadow space, стек для позиций ≥ 4).
